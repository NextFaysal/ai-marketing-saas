## Step 0 — broadcast internals in THIS tree (verified)

**The pipeline.** A `Broadcast` row carries ONE authored `body` (+ `subject`, `htmlBody`) per broadcast. `prepareBroadcast` resolves the audience through the ONE resolver (`resolveBroadcastRecipients` — previous-recipient, recent-days, opt-out-preference, unsubscribed-column, frequency-cap and WhatsApp-opt-in stages, each with honest exclusion counts), applies the deterministic A/B split, builds MS5 per-recipient vars (`buildSnapshotVars`: name/firstName/lastName/email/phone + lastOrderNumber/lastOrderTotal/ordersCount from real Customer/Lead/order rows), and materializes `recipientSnapshot` — Json entries `{ type, id, name, email, phone, status, attempts, vars }`. `processBroadcast` then calls `sendToRecipient` per entry, which renders `renderTemplate(body, { name, ...vars })` (subject and HTML part with the same merge), re-checks opt-out at send time, and only then calls the provider. **The per-recipient substitution point the tree already owns is the snapshot entry's `vars`** — G2 enriches vars at prepare time and forks nothing. WhatsApp sends substitute `{key}` in template params from the same entry vars (`createWhatsAppSender`), so Tier 1 vars flow there too.

**CustomerMemory (SA-B5) as it really is.** Keyed `channel:externalContactId` (conversation channels whatsapp/messenger); facts: `displayName`, `languagePref` (bn | en | mixed — **observed, never guessed**), `topics` (`[{ productId, name, via: "asked" | "ordered" }]`, max 10), `orderCount`, `lastOrderAt`, system notes. There is NO link column from a broadcast recipient to a memory: the only bridge is `ChannelConversation.customerId` / `.leadId` → the conversation's `(channel, externalContactId)` → the memory key. A customer with conversations on both channels has two memories; no cross-channel identity resolution exists and none was invented (the merge rule is recorded in Item 1). Memory refresh is opt-in-gated upstream (conversation learning, D4) — a customer can have orders and no memory; Tier 1 therefore reads live order rows as a second, independent evidence source.

**What does NOT exist (not invented):** per-language template variants (one authored body per broadcast — Tier 1 cannot and does not translate; see Item 1); any LLM money rate anywhere in the tree (Tier 2 cost = call count only); a free-text WhatsApp body (Meta templates only — the MS9 rule that already refuses AI drafts for WhatsApp).

**Existing AI discipline reused.** MS9's shape: platform kill switch (403) → per-bucket daily cap (429) → ONE `AIUsageRecord` per completed call, written after provider success and before parsing; `providerForOrg` via `LlmFactory`; no real LLM ⇒ an honest typed error, never a template dressed as AI. G2's Tier 2 mirrors it under its own bucket (`broadcast_personalization`), exactly as B19 did for `content_generation`.

## Item 1 — BroadcastPersonalizationService + pipeline wiring

`apps/api/src/messaging/broadcast-personalization.service.ts`, registered in `MessagingModule`; `MessagingService` reaches it through an `@Optional` constructor arg with the house lazy fallback (specs constructing the service with the historical 4–5 args keep working — the full MS suite is the regression proof).

**Config.** `Broadcast.personalization` = `{ enabled: true, tier2AiHook?: boolean }`, validated strictly by `normalizePersonalizationConfig` (absent/disabled ⇒ null stored; malformed ⇒ 400; Tier 2 + WhatsApp ⇒ 400). Accepted on create (both channel paths + A/B variants inherit it via the shared base objects), on PATCH (validated against the MERGED body, create's closing-invariant pattern), on clone (content, not send state) and across recurrence chaining (a chain never silently loses its config). With no config, every path is byte-identical to pre-G2 (spec-proven: no tier stamps, no memory vars, zero LLM calls).

**Tier 1 (deterministic, any scale).** At prepare — on the FINAL, post-resolution, post-A/B-split recipient set — `loadRecipientFacts` loads each recipient's own facts: memories via their conversations (merge rule: newest memory wins for language; topics union, ordered-via first), merged with live order evidence (non-cancelled orders → items → products). Derived vars, set only from real evidence: `lastProductName`, `lastCategory`, `favoriteCategory` (mode of bought categories, ties → earliest evidenced), `languagePref`. All five are registered in `messaging/variables.ts` with honest labels. A recipient with no memory and no orders gets their legacy vars back **unchanged** (tier `base`) — their rendered body is byte-identical to the pre-G2 pipeline. Language: facts merge into the ONE authored body; the language stays the author's, because no per-language template variants exist in this tree (recorded, not papered over).

**Tier 2 (AI hook, capped).** Opt-in per broadcast (`tier2AiHook: true`), email/SMS only. The hook is the `{{aiHook}}` variable the author places in the body (the MS5 variable discipline — never a surprise prepend); Tier 2 on without the placeholder is refused at create/PATCH/prepare/preview, before any LLM spend. Eligibility per recipient, all deterministic: channel email/SMS + recipient is a customer + bought categories exist + live candidates exist. A candidate is a LIVE (`ACTIVE`) product in a category the recipient actually bought, excluding products they already bought (cap `TIER2_CANDIDATE_LIMIT = 5`, name-sorted). Generation: ONE `provider.complete` per eligible recipient, grounded in that recipient's fact pack only (their bought names/categories, the candidates with real prices via `formatMinor`, the org's BusinessProfile fields that exist, the staff-authored body); the model may recommend at most one candidate, by exact name, and must return its id — a returned id outside the candidate list, or a name missing from the line, is a fallback (`product`). The shared SA-B3 number guard (`extractGuardNumbers`) judges the line against the recipient's fact pack — an invented number is a fallback (`guard`), as are unparseable output (`parse`) and a provider error (`provider_error`). A fallback never breaks the send: the recipient keeps their Tier 1/base variant, and every fallback is counted with its reason (prepare writes them into the `broadcast.personalised` audit row). Hook language: the recipient's observed `languagePref` when bn/en, else the authored body's detected language.

**Caps and refusals (never silent degradation).** Recipient cap `BROADCAST_TIER2_MAX_RECIPIENTS = 200`: above it, prepare/preview refuse with a 400 naming both numbers. No real LLM + Tier 2 ⇒ typed 503 `{ code: "LLM_NOT_CONFIGURED" }`. Platform AI kill switch ⇒ 403; the day's bucket already exhausted ⇒ 429 (MS9 shapes). Mid-run daily-cap exhaustion falls back per remaining recipient (reason `daily_cap`, counted) — a send already in flight is not killed for later recipients' hooks. Cost surface: LLM **call counts** only (projected for the send, actually-made for the preview) — no LLM money rate exists in this tree, so no price is shown or invented.

**Preview.** `POST organizations/:organizationId/messaging/broadcasts/personalisation/preview` (WRITE_ROLES: OWNER/ADMIN/MARKETING_MANAGER, literal route declared before the `:broadcastId` routes). It runs the SAME resolver (suppression counts included), the SAME `buildSnapshotVars`, the SAME `personaliseRecipients` core prepare runs, and renders samples with `renderPersonalizedBody` — the exported exact merge `sendToRecipient` performs (`renderTemplate(body, { name, ...vars })`; send-time additions every broadcast gets — link tracking, the email unsubscribe footer — happen later in the pipeline and are not part of the render). Tier 2 hooks are generated ONLY for sampled recipients (sample cap `BROADCAST_PERSONALIZATION_SAMPLE_MAX = 5`); counts (total / base / tier1Memory / tier2Ai / tier2Eligible / tier2Fallbacks + fallback reasons) cover the whole resolved set from deterministic facts, plus `tier2LlmCallsProjected` and `tier2LlmCallsMadeForPreview`. Sample labels are name + masked address (CX10 precedent) — never a full address.

**Where the stamps land.** Snapshot entries gain `personalTier: "base" | "memory" | "ai"` ONLY when personalisation was enabled at prepare (absent on every legacy entry; `processBroadcast` reads entries defensively as before and needed no change).

## Item 2 — Specs (`apps/api/src/messaging/g2-personalisation.spec.ts`, 13 tests, all passing)

- **Privacy wall + Tier 1 merge:** two customers with sentinel memories — A's vars/rendered body contain A's product, never B's (and vice versa); a no-memory/no-order recipient's vars are deep-equal to the legacy vars and their rendered body byte-identical to the legacy render; Tier 1 makes zero LLM calls.
- **Cross-org isolation:** org B rows with the SAME customer id, the SAME memory key and an in-category product never enter org A's facts, prompts or candidates.
- **Tier 2 grounding:** hooks recommend the live in-category candidate per recipient (Footwear→GammaSentinel, Bags→EpsilonSentinel); the ARCHIVED in-category product is never offered; each captured prompt contains ONLY that recipient's facts; usage rows land in the `broadcast_personalization` bucket.
- **Out-of-category temptation:** a provider returning the tempting Watches product is refused — tier stays `memory`, no `aiHook`, fallbacks counted with reason `product`.
- **Number guard:** a hook carrying an invented price (Bengali digits) falls back with reason `guard`; Tier 1 facts still merged.
- **Cap refusal:** 201 recipients + Tier 2 ⇒ 400 naming cap and count; zero provider calls.
- **No-LLM honesty:** dev provider + Tier 2 ⇒ typed 503; Tier 1 alone works with no LLM at all. Tier 2 without `{{aiHook}}` ⇒ 400 before any call.
- **Config validation:** normalize rules; `createBroadcast` refuses Tier 2 + WhatsApp and Tier 2 without the placeholder.
- **Suppression first + preview == send:** through the real `MessagingService` — the opted-out customer is excluded by the shared resolver (`excludedSuppressedCount: 1`), appears in no sample/snapshot, and zero LLM calls carry their identity; the preview sample body for cust-a is **byte-identical** to the body the prepared snapshot entry renders; tier stamps (`ai`/`base`) land as expected; preview + prepare call counts reconcile (2 + 2).
- **Legacy regression:** a broadcast without personalisation prepares snapshots with no tier stamps and no memory vars.
- **PATCH discipline:** turning Tier 2 on against a body without `{{aiHook}}` is refused; body + config in one edit succeeds; `personalization: null` turns it off.

## NOT BUILT (G2)

- **Per-language template variants / translated broadcasts** — the tree has one authored body per broadcast and no translation pipeline for sends; Tier 1 merges facts into that body and the language stays the author's. (The Tier 2 hook alone follows the recipient's observed language.) Inventing a translation path was out of scope and would have been fabrication.
- **Tier 2 for WhatsApp** — WhatsApp broadcasts send approved Meta templates; there is no free-text body to personalise, and MS9 already refuses AI generation for the channel. Tier 1 vars DO reach WhatsApp template params through the existing snapshot-vars substitution. Tier 2 + WhatsApp config is a 400, not a silent no-op.
- **Tier 2 for leads / CSV recipients** — the recommendation rule is grounded in bought categories; leads have none by this tree's data, and CSV recipients have no org entity at all. Both still receive Tier 1 where facts exist (leads: their own memory) or the base body. Recorded, not silently skipped.
- **Segments as a new audience mechanism** — none was needed: G2 consumes the existing audience system (customers / leads_stage / RFM segment / custom / saved / csv) exactly as the resolver already exposes it; the plan's "segment অনুযায়ী" is served by personalising within whatever audience the existing segment resolution produced.
- **Web UI** — no composer toggle or preview panel was built; no trivial existing hook presents the personalisation config + preview contract honestly (the composer mirrors `TEMPLATE_VARIABLES`, which now documents the G2 variables, but the config/preview wiring is a web follow-up). The API is complete and tenant-reachable.
- **Live sends / live verification** — nothing in G2 (or the Smart AI line) is proven against a real mailbox, SMS gateway, WhatsApp account or LLM key; M30 remains owed line-wide. The `broadcast_send_sweep` per-org enable is likewise still the owner's.
