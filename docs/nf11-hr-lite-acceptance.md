## Audit findings that shaped the build

- **Staff ARE Membership/User — no parallel people table.** `Membership` (org-scoped, `role`, `status` ACTIVE/INVITED/SUSPENDED) joins `User` (name/email). NF4's `ServiceStaff` is only a bookable-resource view of a membership. Every NF11 row therefore hangs off `Membership` directly.
- **ATTRIBUTION AUDIT FINDING (verbatim):** *The Order model DOES carry a real staff-attribution source. `Order.agentId` — Feature 5 "Team Performance & Staff Attribution": "Staff/Agent who handled, placed, or confirmed the order" — is set by `OrdersService.assignAgent` / `bulkAssignAgent` (PATCH `orders/:orderId/assign` with an `agentId` body field, and the bulk-assign route), and holds the **User id** of the staff member (the staff scoreboard, `OrdersService.getStaffScoreboard`, keys its leaderboard by membership `userId` against `agentId`). `Order.commissionMinor` (BigInt, default 0) is the commission amount **recorded on that order at assignment time** (`assignAgent(orgId, orderId, agentId, commissionMinor?)`). There is **NO org-level commission percentage or per-delivery commission config stored anywhere** in the schema or services; the scoreboard's ৳50 figure is `defaultCommissionBdt`, a **read-time query-param fallback** (default 50) applied inside `getStaffScoreboard` when `commissionMinor` is 0 — it is never stored, never configured per org, and is **NOT used by NF11** (using it would fabricate pay). `Order.assigneeId` (ON1) is a separate work-queue assignee and is not the sales-attribution field.*
- **NF10 journal door:** `AccountingService.createJournalEntry(orgId, actorId, {date, memo, sourceType, sourceId, lines})` is a clean public programmatic door (balance invariant + `(org, sourceType, sourceId)` idempotency built in), and NF10's `DEFAULT_ACCOUNTS` already contain **Expense: Salary (code 5210, systemKey `expense_salary`)** and **Cash (1000, `cash`)** — so the payroll entry needs **no seeding extension**. Account ids are resolved through the public `listAccounts` payload (which carries `systemKey`). The integration therefore **composes cleanly and IS BUILT** (see verdict below).
- **PDF machinery:** the same dependency-free toolkit NF10 used (`apps/api/src/courier/pdf.ts` — `PdfCanvas` + `buildPdf` + `moneyText`). Its WinAnsi limit applies unchanged: Bengali renders as "?" in PDF bytes, so the payslip carries English labels/glosses for every amount and line in the PDF; full Bengali lives in web + JSON.
- **Org timezone EXISTS:** `Organization.timezone` (default `Asia/Dhaka`) — attendance days, leave/payroll month boundaries all use it via NF4's Intl-based `localParts` (reused from `booking/slots.ts`). No fallback was needed; the code still defaults to Asia/Dhaka if the field were ever absent.
- **NF4 availability shape reused:** `StaffShiftPattern` mirrors `StaffAvailability` field-for-field (weekday 0=Sunday…6, `startMinute`/`endMinute` minutes-from-midnight, same validation: end > start, ≤1440), keyed to the Membership instead of a ServiceStaff resource.

## Design decisions

- **Stored, explicit payroll rules (`HrSetting`, one row per org):** `unpaidLeaveRule = "per_calendar_day"` (v1's only value — deduction = round-half-up(`base × approved-unpaid days overlapping the month ÷ days-in-month`), capped at the base) and `commissionRule = "recorded_order_commission"` (v1's only value). Unknown rule values are refused at the setting API **and** re-checked at run generation (an unknown stored rule blocks the run rather than silently computing something else). Both rules' plain-language texts ship in the setting payload and in the UI.
- **Payroll computation (draft generation):** for each **ACTIVE** membership whose salary profile is **effective in the month** (`effectiveFrom` org-local date ≤ month end): base = profile base; unpaid days = Σ overlap of **APPROVED + unpaid** `LeaveRequest`s with the month (pending/rejected/paid leave deducts **nothing** — spec-proven); commission = Σ recorded `Order.commissionMinor` over **sold** orders (`completed | delivered`, the canonical NF7/EC33 half) with `agentId = membership.userId` and order date (`placedAt ?? createdAt`, org timezone) in the month. An attributed order recorded with `commissionMinor = 0` contributes **0** — no rate, no per-delivery default, nothing invented (spec-proven: a member with two delivered attributed orders at 0 recorded commission gets `commissionMinor = "0"`). Commission beyond the recorded source can only enter as an **explicit manual adjustment line with a note** on a draft line.
- **Rule snapshot:** every run stores `ruleSnapshot` — both rule names, days-in-month, month bounds, timezone, sold statuses, the commission-source statement, generation time, and **per-member inputs** (base, effectiveFrom, unpaid days + the leave request ids counted, attributed sold-order count, recorded commission sum). The dashboard shows it verbatim (JSON) on the run.
- **Run lifecycle:** one run per org per (year, month) (schema unique). Regenerating a **draft** replaces its lines in place and re-snapshots. Lines are editable **only while draft** — adjustments replace the line's adjustment list (each entry requires a non-empty label **and** note and a non-zero signed amount; the edit is audit-logged with the full adjustment payload) and the line/run totals recompute from the single formula `total = base − deduction + commission + Σ adjustments`. A **paid** run is immutable: regenerate / adjust / re-mark-paid all refuse (spec-proven).
- **Mark-paid (OWNER-only route, `@Roles("OWNER")` exactly):** draft → paid stamps `paidBy`/`paidAt`. **It is a RECORD, not a money movement** — stated in the run payload (`recordNote`, Bengali + English), the API doc-comment, the dashboard banner, the run detail, and the payslip PDF.
- **NF10 INTEGRATION VERDICT: BUILT.** On mark-paid with a positive run total, the service posts **ONE** journal entry through `AccountingService.createJournalEntry`: **Dr Expense: Salary / Cr Cash**, amount = run total, `sourceType = "payroll_run"`, `sourceId = run id` (NF10's unique makes a repeat impossible; the run also stores `journalEntryId`). A zero-total run posts nothing (the door refuses zero entries by design). The posting is **failure-isolated** in the Finance-hook pattern: if accounting is unavailable or errors, the paid RECORD still stands and the response reports `journalPosted: false` + `journalError` — a journal failure never un-pays or blocks the record, and the entry can be reconciled manually. Spec-proven against a recording AccountingService fake (the real door's balance invariant is proven in NF10's own suite): exactly one call, balanced Dr = Cr = run total, correct accounts, and no second post on a re-mark attempt (which refuses earlier, on status).
- **Attendance:** one record per member per org-timezone day (schema unique). Self check-in/check-out act **only on the caller's own** record (the self routes take no membershipId at all — the service resolves the caller to their Membership). Corrections are OWNER/ADMIN-performed, require a `correctionNote`, set `source = "staff_correction"`, store the note, and **always** write an AuditLog entry (`hr.attendance_corrected`, via a direct `AuditService.log` call, not the failure-swallowing wrapper) — spec-proven.
- **Leave state machine:** `pending → approved | rejected` only; a decided request can never be re-decided (spec-proven). `days` is the inclusive calendar-day count computed server-side. Only **approved + unpaid** days feed payroll.
- **Payslips:** generated **from the stored `PayrollLine`** (the same `lineView` numbers the run shows) — never recomputed — so payslip total == line total == run-total component by construction (spec-proven, incl. a real `%PDF-` buffer containing the total row). The self payslip path re-resolves the caller's membership and refuses another member's line (spec-proven); admins use the staff route.
- **Roles/guards:** `@PermissionArea("team")` + TenantGuard/RolesGuard like the neighbouring modules. Salary-profile writes, setting, corrections, shifts, leave decisions, run generation and line edits are OWNER/ADMIN; reads use the four-role staff set; mark-paid is OWNER exactly; the `me/…` self surface is open to every member role (hierarchy minimum VIEWER) and is own-records-only in the service, so even a forged membershipId cannot reach another member's data (the self DTOs don't carry one).

## NOT BUILT / limits

- **No live proof of anything:** no NF11 migration has run on a real database, no real member has checked in, no payroll journal entry has posted against a real NF10 chart, nothing is deployed. Fresh-PG + boot smoke are the coordinator finisher's gates for FB4; M30-style live verification is still owed (note for the boot smoke: `AppModule` gains `HrModule`, which imports `AccountingModule` + `AuditModule` — no cycle expected, the smoke is the proof).
- **Mark-paid moves NO money** — no bank/mobile payout, no gateway, no cash disbursement integration. It is a record (+ one journal entry). Paying staff still happens outside the system; the profile's `payoutNote` is a free-text reminder only and must never hold credentials.
- **No salary-profile history:** one current profile per membership (upsert replaces it); a profile edited mid-month changes the next draft generation — past **paid** runs keep their stored lines/snapshot and never change, but there is no effective-dated profile versioning beyond the single `effectiveFrom`.
- **Commission is exactly the recorded source:** orders attributed via `assigneeId` (ON1 work queue) do NOT count; un-attributed orders count for nobody; a negative recorded `commissionMinor` would be summed as recorded (assignment accepts a staff-entered number — payroll trusts the record, as designed). No percentage-of-sales or per-delivery rule exists because no such config exists in the codebase (see the audit finding) — adding one is an owner decision for a later batch.
- **No attendance reports/exports, no late/absent derivation** (attendance is check-in/out records + corrections only; absence is not inferred from missing records), no geolocation/IP capture on check-in, no leave balance/accrual quotas, no leave calendar view, no recurring shift templates beyond the weekly pattern, no per-member shift exceptions/overrides for single dates.
- **Payroll granularity:** monthly runs only; no mid-month/off-cycle runs, no per-run member inclusion/exclusion toggles (every ACTIVE member with an effective profile is included), no tax/TDS computation, no payslip email/SMS send (download only), no multi-currency payroll (amounts are minor units of the org's books, as recorded).
- **Payslip PDF Bengali glyph limit** (see Audit): the PDF carries English labels/glosses through the WinAnsi toolkit; the verbatim Bengali record note renders as "?" glyphs inside the PDF bytes — full Bengali renders on the web page and in every JSON payload. A font-embedding PDF stack was not built.
- Full API jest, fresh-PG and boot smoke were **not** run — per the FB4 brief they belong to the coordinator's serial finisher.
