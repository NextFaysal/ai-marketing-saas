## Audit findings that shaped the build

- **Existing finance is view-only.** OU7/GB8's `Expense` model + `FinanceService` compute ledgers and a GL export as VIEWS over source records — there was no chart of accounts and no persisted journal anywhere. NF10 adds the persisted double-entry layer WITHOUT forking or breaking any of it: the GB8 ledgers, reports and GL export are byte-unchanged, and `Expense` keeps its exact model/API/UI.
- **"Verified payment" = `PaymentVerification.status = "approved"`** (the EC19 verdict field; inbox-extracted rows sit `pending` until staff approval, staff advances are born `approved`). Pending/rejected rows never generate entries — spec-proven.
- **Sold statuses = `completed | delivered`** — the codebase's canonical NF7/EC33 order-status half, used verbatim for revenue recognition.
- **COGS data EXISTS:** `ProductCost` (productId, nullable variantId, `costMinor`, `effectiveFrom`). `OrderItem` carries NO variant id, so the cost pick is the product-level row (variantId null) with the latest `effectiveFrom`, falling back to the latest row of any variant of that product.
- **Courier charge field EXISTS (two of them):** `CourierShipment.chargeMinor` (GB5 — the `delivery_fee` the provider returned at booking; null when none) and the stronger `ReconciliationLine.sheetChargeMinor` (the charge on the courier's own EC26 settlement sheet). Generation prefers the sheet charge, falls back to the booking charge, and SKIPS a shipment with neither — no charge is ever estimated or invented.
- **VAT config EXISTS:** `TaxSetting.defaultVatBps` (EC23; null = tax off / not configured) + `pricesIncludeVat`. The VAT summary reads the rate from there and never invents one.
- **PDF machinery:** the dependency-free toolkit in `apps/api/src/courier/pdf.ts` (`PdfCanvas` + `buildPdf`, used by labels/invoices/challans) is reused as-is for both report PDFs.

## Design decisions

- **AR / revenue design (the one coherent design):** revenue is recognised at the sold order — Dr Accounts Receivable (order total), Cr Sales Revenue (total − shipping − tax, i.e. net merchandise incl. any remainder, so every entry balances by construction), Cr Delivery Income (shippingMinor), Cr VAT Payable (taxMinor). A verified payment then SETTLES the receivable — Dr Cash/bKash/Bank by `PaymentVerification.provider`, Cr Accounts Receivable — and touches NO income account, so revenue is never double-counted. Within one sync run, revenue entries are generated BEFORE payment entries. A payment synced before its order's revenue entry temporarily drives AR negative for that order until the revenue entry lands; this is stated, not hidden.
- **Balance invariant at the ONLY write door:** `AccountingService.createJournalEntry` validates before any write — ≥2 lines, each line exactly one positive side, Σdebit == Σcredit and Σ > 0, every account org-owned. Unbalanced entries throw a Bengali 400 and NOTHING is saved (spec-proven for unbalanced / single-line / zero / both-sided / foreign-account attempts). Manual entries ride the same door (`sourceType = "manual"`, null sourceId).
- **Idempotency:** auto-entries carry `(organizationId, sourceType, sourceId)` — `order` / `payment` / `expense` / `courier_charge` — backed by the schema unique; the service pre-checks and also replays on a unique violation. Re-running the sync creates zero duplicates (spec-proven for orders, payments via the expense hook + sync, expenses).
- **Auto-generation entry points (documented choice):** (1) an explicit idempotent sync — `POST accounting/sync`, also invoked at the head of both reports, in the NF7-reconciler spirit (derived state, always rebuildable); (2) a forward hook: `FinanceService.createExpense` journal-backs a NEW expense immediately (failure-isolated; the expense stays the source truth and the sync can backfill). Existing expenses backfill through the same sync. Expense EDIT/DELETE deliberately do NOT rewrite journal history in v1 (see NOT BUILT) — the original entry stands as the audit record.
- **COGS gap handling:** COGS posts (Dr COGS / Cr Inventory, inside the order's entry) ONLY when EVERY item line has a real `ProductCost`. If any line lacks a cost (no linked product or no cost row), the order's COGS is omitted ENTIRELY (a partial COGS would understate cost) and the order is counted in `cogsMissingOrders` — surfaced in the sync result, the P&L payload (`cogsNote`), the P&L page and the P&L PDF. No cost is ever invented.
- **Courier charges:** Dr Courier Charges / Cr Accounts Payable per shipment, first known charge wins — an entry, once created, is NOT revised if a later settlement sheet shows a different charge (documented v1 limit; the discrepancy remains visible on the EC26 mismatch surfaces). Shipments whose only charge evidence arrives later still generate on the next sync, because generation is per-shipment idempotent, not a one-shot backfill.
- **Chart of accounts:** 20 BD-retail system defaults (Cash 1000, bKash 1010, Bank 1020, Accounts Receivable 1100, Inventory 1200, Accounts Payable 2000, VAT Payable 2100, Owner Equity 3000, Sales Revenue 4000, Delivery Income 4100, Other Income 4200, COGS 5000, Courier Charges 5100, and one expense account per OU7 category — `delivery` maps onto Courier Charges). Seeded LAZILY per org on first accounting use, idempotently by `systemKey`; a staff custom account that already took a default's code is never overwritten. System accounts: rename allowed, delete/retype refused (service-enforced). Custom accounts: deletable/retypable only while unused in the journal. Default names are English so the WinAnsi PDF toolkit renders them; staff may rename freely (the journal stores account ids, never names).
- **Statement reconciliation — extension, not a fork:** bank/mobile-banking imports live on the EXISTING `ReconciliationImport`/`ReconciliationLine` tables with `kind = "bank_statement"`, `courierIntegrationId = null`, the absolute amount on `sheetAmountMinor` (the sheet-amount column, as EC26), and the new `statementDate` / `description` / `direction` / `matchState` / `suggestedRefType` / `suggestedRefId` columns. Courier rows are untouched (`kind` defaults to `courier_cod`). File-hash dedupe follows the EC26 pattern (same file refused without `force`). Matching SUGGESTS by amount + ±3-day window against (a) cash/bKash/bank journal lines (credit statement line ↔ debit journal line, debit ↔ credit) and (b) approved payment verifications (credit lines only). **Nothing auto-confirms** — a suggestion sets `matchState = "suggested"` only; a staff `confirm` (which re-verifies the counterpart belongs to the org) sets `matched`, `reject` sets `rejected`, both stamping reviewer + time (spec-proven: after import, zero lines are `matched`).
- **Reports are journal-ONLY:** monthly P&L aggregates `JournalLine`s of entries dated in the Dhaka month (income = Σ credit−debit, expenses/COGS = Σ debit−credit; gross = income − COGS; net = gross − other expenses). The VAT summary reports the VAT Payable account's month credits (collected), month debits (paid), month net and cumulative balance, names the account it used, and shows the `TaxSetting` rate as CONFIG CONTEXT only (amounts are never recomputed from the rate; with no configured rate it says so and shows journal amounts alone).
- **Disclaimer:** `এটি একটি হিসাব-সহায়ক টুল — অডিট করা বা বিধিবদ্ধ হিসাব নয়।` appears verbatim in the P&L/VAT JSON payloads, the sync payload, the accounts payload, the statement payloads, twice on the ledger page (banner + report card + statement card), and in both PDFs. PDF caveat (the toolkit's own documented limit): `courier/pdf.ts` renders WinAnsi text only, so the Bengali disclaimer string is passed through `pdfText` and its non-WinAnsi glyphs render as "?" in the PDF bytes — the PDF therefore ALSO carries the English gloss line "Accounting aid tool - not audited or statutory accounts." directly above it. The verbatim Bengali disclaimer is fully rendered on the web page and in every JSON payload; making it glyph-perfect inside the PDF would require a new font-embedding PDF stack, which is NOT BUILT (see below).

## NOT BUILT / limits

- **No live proof of anything:** no NF10 migration has run on a real database, no real bank statement has been imported, nothing is deployed. Fresh-PG + boot smoke are the coordinator finisher's gates for FB4; M30-style live verification is still owed.
- **Expense EDIT/DELETE do not rewrite the journal:** editing or deleting an `Expense` after its entry exists leaves the original journal entry standing (the audit record); staff correct it with a manual reversing entry. The create-path hook + sync cover creation and backfill only.
- **Courier entries are not revised:** first known charge (sheet preferred at generation time) wins; a later differing sheet charge does not amend the entry (see Design).
- **Revenue uses order-STATUS only** (`completed | delivered`, the NF7 canonical half): an order sold via a delivered SHIPMENT while its own status lags (the finance `isSoldOrderShape` shipment half) does NOT recognise revenue in v1 — the status-only rule is the brief's and NF7's, and it keeps "pending/cancelled create none" absolute.
- **No inventory valuation / FIFO / average-cost:** COGS is Σ latest-ProductCost × qty at generation time; later cost edits do not restate past entries. Variant-level costing is approximated as documented (OrderItem has no variant id). Orders with zero/negative totals and no COGS create no entry.
- **No VAT return filing, no VAT on purchases/input credit, no multi-currency journal, no period locking/closing, no journal edit/delete UI** (the journal is append-only by design; corrections are manual reversing entries via the API — the manual-entry UI is the API + the accounts/journal views on the ledger page, per brief). Account create/edit from the web page is API-only in v1 (the page lists accounts + balances; renaming is an API call).
- **Statement matching is suggestion-only with a ±3-day window and amount equality** — no fuzzy/partial matching, no split matches, no auto-confirm of any kind, and confirming a line does NOT itself post a journal entry (it records the reconciliation link only). Statement CSVs arrive as pasted text (the EC26 pattern), not file upload; direction comes from an optional direction column or the amount's sign.
- **PDF disclaimer glyph limit** (see Design): the Bengali disclaimer renders as "?" glyphs inside the PDF bytes through the existing WinAnsi toolkit; the English gloss line carries the same meaning in the PDF, and the verbatim Bengali renders on the page + JSON. A font-embedding PDF stack was not built.
- Full API jest, fresh-PG and boot smoke were **not** run — per the FB4 brief they belong to the coordinator's serial finisher (note: `AppModule` gains `AccountingModule`; `FinanceModule` now imports `AccountingModule` for the expense hook — the boot smoke is the gate that must confirm the new routes map and no DI cycle exists).
