# SP8 Acceptance — TikTok (OAuth Connect + Inbox Upload)

Package: Social Media Post Scheduler, Batch 5 item 1 (plan: `docs/social-posts-package-plan.md`, amendment section). Builds on SP1–SP7 (Meta connect/schedule/publish/insights/approval — untouched except the shared publish dispatch gaining a TikTok branch and `SocialPost.publishNote`).

## What shipped

### Shared groundwork (also serves SP9)
- **Platform config blocks** (`common/platform-config.ts`): `tiktokApp` { clientKey, clientSecret (sealed), redirectUri?, audited } and `googleApp` { clientId, clientSecret (sealed), redirectUri? } — SystemSetting keys `tiktokAppConfig` / `googleAppConfig`, snapshot + `effectiveTiktokAppConfig()` / `effectiveGoogleAppConfig()` resolvers with the house admin → env discipline (env: `TIKTOK_CLIENT_KEY/SECRET/REDIRECT_URI`, `TIKTOK_APP_AUDITED=true`, `GOOGLE_CLIENT_ID/SECRET/REDIRECT_URI`). A key WITHOUT a secret resolves as **not configured** — the token exchange could never succeed with half a config.
- **Admin API**: `PATCH /admin/platform-config/tiktok` and `PATCH /admin/platform-config/google` (SUPER tier), merged into `GET /admin/platform-config`'s safe view (secrets reported only as `secretConfigured` booleans; audit records field NAMES only). Admin Console (Settings → Dynamic Platform Config) gained a TikTok App card (with the operator's **audited** declaration checkbox) and a Google App card, each stating the exact redirect URI to register with the platform.
- **OAuth state** (migration `20261010960000_sp8_oauth_state_publish_note`): new `SocialOAuthState` table. The state value IS the row id (32 random bytes, base64url), binds org + user + platform + purpose, expires in 10 minutes, and is **single-use** — consumed via a conditioned `updateMany` (SP5 claim style), so a replayed callback can never succeed twice. Chosen over a stateless signed token because SP9's channel-picker step needs a server-side pending payload anyway; one mechanism serves both.
- **`SocialPost.publishNote`** (same migration): an honest platform-state note recorded WITH a successful hand-off and shown verbatim in the UI. Null for plain Meta publishes.

### SP8 — TikTok
- **Connect**: `GET organizations/:id/social/accounts/tiktok/connect-url` (OWNER/ADMIN) — placed under `accounts/` following the module's own Meta convention (`accounts/meta/discover`); the brief's literal path was `social/tiktok/connect-url`. Not configured → the honest Bengali 400 ("TikTok app এখনো configure করা হয়নি — Platform Operator-এর সাথে যোগাযোগ করুন…"), never a broken authorize URL. Scopes: `user.info.basic,video.upload`; `video.publish` joins ONLY when the operator declared the app audited (config-driven, default upload-only).
- **Callback**: `GET /social/oauth/tiktok/callback` (public, `@Public()`): validates + consumes state strictly; exchanges the code (`POST /v2/oauth/token/`), fetches the creator (`/v2/user/info/`), and persists Integration (provider `tiktok_social`) + AES-256-GCM sealed credential { accessToken, refreshToken, expiresAt, refreshExpiresAt, scope, openId } + SocialAccount { platform `tiktok`, externalId = open_id, name = display_name } with SP1's supersede hygiene (a previous CONNECTED integration for the same identity is torn down only when zero accounts reference it). EVERY outcome is a 302 to the web app with `social_connected=tiktok` or a `social_error` explanation — platform error params, missing code/state, unknown/expired/replayed state, exchange failure (TikTok's verbatim message) included. Never a 500.
- **Token refresh**: the shared resolver (`SocialOAuthService.ensureAccessToken`) refreshes inside a 60-second skew window via TikTok's refresh grant (TikTok ROTATES the refresh token — the new pair is re-sealed), and a failed refresh marks the account `error` + `lastError` (verbatim) and fails the publish permanently — retrying a dead refresh token can never succeed, so no attempts are burned.
- **Publish** (same SP5 worker + SP7 approval re-check; the platform switch in `SocialPublishService.publishToPlatform` gained the OAuth branch):
  - Media gate: TikTok posts require EXACTLY ONE video — image/multi/none is a `PermanentPublishError` with the Bengali reason, attempts untouched; `schedulePost` refuses the same posts up front with a Bengali 400.
  - **Default (unaudited) = Inbox Upload**: `POST /v2/post/publish/inbox/video/init/` with `PULL_FROM_URL` against the asset's SP1 public URL (auto-minted by the publish path, exactly like SP6's Instagram flow), then bounded status polling until `SEND_TO_USER_INBOX`. Result: status **`sent_to_creator`**, `platformPostId` = publish_id, `publishedAt` stays **NULL**, `publishNote` = "ভিডিওটি TikTok Creator-এর Inbox-এ পাঠানো হয়েছে — TikTok app-এ গিয়ে post সম্পূর্ণ করুন। এটি এখনো প্রকাশিত (published) নয়।" Honest limitation of the inbox flow: the caption cannot travel with an inbox upload — the creator writes it in the TikTok app; the composer says so when a TikTok account is selected in inbox mode.
  - Status `FAILED` → ordinary publish failure with TikTok's `fail_reason` verbatim (SP5 backoff/retry semantics). Poll exhaustion → ordinary error naming the publish_id; a retry starts a new upload (a duplicate draft may land in the creator's inbox — the documented at-least-once class of SP5, benign here).
  - **Direct post (audited only)**: when `tiktokApp.audited` is true, the adapter queries `creator_info` first and uses ONLY the privacy levels it returns (`PUBLIC_TO_EVERYONE` when offered, else the first returned option) with `/v2/post/publish/video/init/`; `PUBLISH_COMPLETE` → status `published` with the used privacy level recorded in `publishNote`. Default OFF; the account card labels the mode ("Inbox mode — audit বাকি" vs "Direct post mode").
- **UI**: TikTok connect button (disabled with an explanation when the operator hasn't configured the app), account-card mode label, composer hint when a TikTok/YouTube account is selected (exactly-one-video rule + the inbox caption note), `publishNote` shown on post cards and the post detail, OAuth return params surfaced once and stripped from the URL.

## Evidence — boundary, NOT live (ceiling stated plainly)

**No real TikTok round-trip happened.** This sandbox has no Postgres binary and no real TikTok app; OAuth, the inbox flow and the direct-post path are proven at the client boundary with a labelled stub fetch + fake Prisma, plus the full suite and builds:

- New spec `apps/api/src/social/social-sp8.spec.ts` — 22 tests: config resolution (admin/env/half-config), admin PATCH sealing + safe-view non-disclosure, connect URL (not-configured 400, scopes default vs audited, state binding), callback (platform error, happy path with sealed-credential round-trip + token-free audit, replay rejection, expiry, verbatim exchange failure), publish dispatch (inbox → `sent_to_creator` with `publishedAt` NULL, image/multi permanent failures with attempts 0, audited direct → published with privacy note, FAILED → verbatim retry path), client boundary (PULL_FROM_URL body, error-envelope verbatim, token-exchange form), refresh (rotation re-sealed, fresh-token no-op, failure marks account error), schedule gate.
- Full API suite + web tests + monorepo build: see the batch report for final numbers.

## What the owner must do for the live (M30-style) proof

1. Register a TikTok app at developers.tiktok.com with the Login Kit + Content Posting products; set the redirect URI to `https://api.qosprey.com/social/oauth/tiktok/callback`.
2. Admin Panel → Settings → Dynamic Platform Config → TikTok App: paste Client Key + Client Secret (leave "audited" OFF until TikTok approves the app for direct posting).
3. Tenant Social Posts page → "🎵 TikTok যুক্ত করুন" → authorize → schedule a one-video post → confirm the video lands in the TikTok app's inbox/drafts; finish the post in the app.
