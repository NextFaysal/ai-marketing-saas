## ON3 — Order Surgery, delivered

### The one-calculator invariant
`PromotionsService.evaluateCheckout` already accepts caller-priced lines, so surgery needed **no evaluator change**: pinned prices are passed as `unitPriceMinor`, and every post-surgery total comes out of the one evaluator (parity is spec-pinned against the real evaluator as oracle for plain / promotion / coupon / referral carts). Total formula matches checkout exactly: `subtotal − discount + delivery + taxAdded + giftWrap`. Cart construction mirrors checkout semantics: catalog lines (productId set, non-gift) go to the evaluator; non-catalog lines (productId null, e.g. `ADD-ON-BUMP`) are summed into `bumpMinor`; gift lines never enter the evaluator (spy-asserted); the evaluator's gift candidate is ignored by surgery in both directions — an edit never adds or removes a gift.

### The coupon problem (finding + rule)
**Finding:** until this batch the applied coupon CODE was stored nowhere on the order (only its amount, derivable as `discountMinor − promotionDiscountMinor − referralDiscountMinor`); `DiscountsService.redeem` keeps no per-order record. Two-part fix:
- Going forward, `PromotionsService.stampOrder` now also stamps `Order.couponCode` whenever a coupon truly applied (`appliedDiscountId != null`), so future orders carry their code.
- Surgery's rule: an **explicit code** (DTO `couponCode`, or the stored stamp) is re-validated through the evaluator — invalid ⇒ dropped, `couponDropped: true`, stored code cleared, never silently kept. A **legacy order** (derived coupon discount > 0, no code anywhere) keeps its derived amount as a disclosed pin: `couponPinnedMinor` in the response + a Bengali warning + an audit flag — never presented as validated. An **explicit `couponCode: null`** is a deliberate drop and never falls into the pin branch (a spec caught the literal reading keeping ৳200; fixed).
- Referral re-evaluates with the order's own `referralCode`: the evaluator's first-use rule now counts the order itself as the prior use, so an edit typically drops the referral discount — surfaced as `referralDropped: true`, never hidden. (A future self-exclusion in `resolveReferral` is the possible remedy; deliberately not smuggled into this batch.)

### Stage safety matrix (as implemented; every violation is a Bengali 400 naming the blocker)
Common guard for items-edit / split / merge participants: not practice; not ON4 review-held (release first); status ∈ {pending, on-hold, processing}; **store boundary (below)**.
- **Item edits:** a changed/removed line covered by a non-cancelled fulfillment in a non-`pending` status ⇒ refused; a `pending` fulfillment whose quantity for the line exceeds the new quantity ⇒ refused. A shipment in {picked_up, in_transit, out_for_delivery, delivered, partial_delivered} ⇒ refused; a booked (`in_review`) shipment does NOT block but the response warns the courier label/manifest may be stale (the shipment is NOT auto-cancelled).
- **Split:** additionally — no active (non-cancelled) shipment at all (booking is order-level); no non-cancelled fulfillment covering a moved line; moved quantity ≤ line quantity; at least one line must remain; gift lines cannot move; bundle groups move whole or not at all.
- **Merge:** 2–5 orders, survivor ∈ the set; every participant passes the common guard AND has no active shipment and no non-`pending` fulfillment; same customer (same `customerId`, or different customer rows sharing one normalized phone key via the ON11 util — customerless orders cannot merge in v1); same currency; no participant already merged away.
- **Merged orders are closed:** `OrdersService.updateOrder` refuses status changes and refunds on orders with `mergedIntoId` set (note/address edits still allowed).

### Operations
- **PATCH `orders/:id/items`** with a full desired line set (omission = removal) + **POST `orders/:id/items/preview`** running the identical computation with no writes, no stock, no audit. New lines price from the catalog NOW (variant-aware) unless a staff `unitPriceMinor` override is given (recorded in the audit diff as a count; overrides refused on gift and bundle-component lines). Delivery is preserved unless `recalculateDelivery: true`, which re-runs the real `StorefrontService.matchZone` + `resolveDeliveryCharge` (OrdersModule → StorefrontModule import verified cycle-free; DI spec green) on the customer's stored district; pickup orders keep the point's fee. Stock moves per-line through the new inventory delta path (below). Audit `order.items_edited` carries added/removed/changed lines, totals before/after, `couponDropped`/`couponPinned` flags. Response includes `overpaidMinor` when approved verifications exceed the new total (computed, not stored; no auto-refund exists — the EC9 refund flow is the remedy), plus warnings (stale shipment; a store draft, when present, no longer matches).
- **Bundles (EC29):** component lines cannot be edited or removed individually (400). A group is addressed by one `{ bundleId, quantity }` entry (omission removes the whole group) and re-priced by re-running the existing `allocateBundle` with the order's *implied* original bundle price (Σ stored component totals ÷ current bundle quantity — exact by the EC29 identity), so the customer keeps their order's price even if the bundle's price changed since.
- **Split (POST `orders/:id/split`)**: the child is created by direct Prisma writes — deliberately NOT via `upsertOrder`, so there is no second stock decrement, no `order.ingested` (no fraud stamp, no `order_placed` notification, no workflow storm). Child: `source` = original's source, `externalId = split-<uuid>`, external number in the native `ORD-…` style (native orders have no numeric sequence — this is the honest adaptation of "next in sequence"), `splitFromId` set, status/payment copied, delivery slot/pickup NOT copied (slot capacity was counted against the original), delivery charge = staff value or 0 (stated in the response), promotions re-evaluated on the moved cart, coupon/referral NOT carried over. PaymentVerifications stay on the original (response states this). The original is recomputed over its remaining lines under the normal edit rules.
- **Merge (POST `orders/:survivorId/merge`)**: route nests under the survivor id so no literal segment can collide with `:orderId` routes (documented adaptation of the planned `orders/merge`). Identical product+SKU+pinned-price lines sum quantities; differing prices stay separate lines. Survivor keeps its own delivery charge; the others' charges are dropped and reported as `droppedDeliveryMinor`. Non-survivors are cancelled by direct write (status + appended internal note + `mergedIntoId`) — `updateOrder` is NOT called, so no stock restore and no status events fire; their pending fulfillments are cancelled; their PaymentVerifications are reassigned to the survivor with the trx ids and approval states intact (audit per reassignment batch), so the survivor's due math stays true.
- **Stock truth across surgery:** new `InventoryService.applyOrderEditDelta` (reason `order_edit`, SKU-rule variant resolution with NO product↔variant fallback, preorder/untracked skips, EC4 bundle components moved proportionally with signed amounts, low-stock alert + stock push mirrored from placement) and a Phase B appended to `applyOrderRestore`: after the unchanged Phase A replay, the restore nets every key across {order_placed, bundle_component, order_edit} against what was already restored and writes only the diff — naturally idempotent (a second restore computes diff 0). Split/merge move stock ownership through `recordStockTransfer` (ledger-only movements, **balances never change**: from-order `order_edit` +qty, to-order `order_placed` −qty for sold lines / `bundle_component` −qty for components). Spec-proven end-to-end: edit→cancel returns stock exactly to baseline; a split child's cancel restores exactly the moved quantity and the original's cancel exactly the remainder; a survivor's cancel after merge restores the FULL combined quantity.
- **Roles:** all surgery writes are `@Roles("OWNER", "ADMIN", "MARKETING_MANAGER")` (SUPPORT_AGENT excluded, the create-store-draft precedent).
- **Store-order boundary (v1, loud):** the outbox has pushes for status, refund, note, address, and fulfillment — but NO order-items/totals update push exists. Item edits, split, and merge are therefore refused for `woocommerce`/`shopify` orders (totals would diverge from the store, which owns their truth). Address edits on store orders continue through the existing PATCH path, which already enqueues `push_order_address`.

## ON7 — Profit & খাতা, delivered

### ProductCost as-of rule (as implemented)
Costs are read from the `ProductCost` history (orders snapshot no cost at placement). Per line: the line's variant resolves by the (productId, SKU) rule. The applicable set is the variant-specific rows when the line has a variant and such rows exist, else the product-level (`variantId = null`) rows. Within the set: the latest `effectiveFrom ≤ placedAt`; if none, the earliest after `placedAt`; if the set is empty the line is **uncosted** — no number is invented. Gift lines cost real money and are costed like any line; bundle component lines are real lines and are costed individually.

### Delivery actual (finding)
**`CourierShipment` carries NO courier-charge field.** The only real actual-charge source in the system is `ReconciliationLine.sheetChargeMinor` — the charge column from the merchant's own imported settlement sheet (EC26). Per shipment, the actual charge is the earliest matching line (`matchedShipmentId` = shipment, `sheetChargeMinor != null`, outcome ∈ {matched, amount_mismatch, already_collected}). `deliveryActualMinor` — and therefore `netMarginMinor` — is reported **only when the order has ≥ 1 shipment and EVERY shipment has such a line**; otherwise both are null and `deliveryActualCoverage { shipments, withCharge }` shows the partial truth. An order whose courier sheet was never imported shows no "actual" and no net margin — by design, not by omission.

### Surfaces
- `GET orders/:orderId/profit` — revenue (order total), discount, delivery charged, product cost (null when zero lines costed), costed/uncosted line detail with the uncosted revenue stated, gross margin, delivery actual + coverage, net margin (rules above).
- `GET orders/reports/profit?from&to` (+ `.csv` in the EC23 export style) — over the **EC33 sold bucket** (predicate mirrored exactly from `purchasing/inventory-intelligence.service.ts:isSoldOrder`, with a pointer comment — importing PurchasingModule would cycle): status ∉ dead states AND (status completed/delivered OR a delivered/partial_delivered shipment). Totals state the costed-revenue coverage %; `perProduct` is sorted by margin ascending with unknown (null) margins LAST — unknown is never presented as worst — capped at 100 with a `truncated` flag; per-product revenue is pre-discount line totals and is labelled as such (`perProductBasis`), while totals revenue is post-discount order totals.
- **Customer খাতা** — `Customer.creditLimitMinor` (staff-set, null = no limit; garbage values get a Bengali 400). `GET customers/:id/khata`: per-order total/paid/due from the one EC19 rule (approved verifications only), open dues exclude cancelled/refunded/returned/failed orders, aging buckets 0–7 / 8–15 / 16–30 / 30+ days by order age, `overLimit`, and `availableCreditMinor` returned as the true signed value (it can be negative — never floored). Customers list rows gain `dueMinor` (one grouped pattern, no N+1) + a `hasDue` filter that filters before the page slice. Web: খাতা section in the customer detail with aging tiles + credit-limit editor; COD board + profit report sections in `dashboard/commerce/accounting`.
- **COD board** — `GET orders/reports/cod-board`: per provider, in-transit COD (shipments in the ON1 transit statuses, uncollected), delivered-but-uncollected, collected in the last 7 days (EC26 `codCollectedAt` stamps), outstanding; plus an `unassigned` bucket — COD orders with real due and NO shipment at all, labelled "এখনো courier-এ যায়নি". The UI caption says the money is *with the courier*; no arrival promise is made anywhere.

## Honest limits

- **Process note (stated plainly):** two of the three builders and one finisher instance were lost to sandbox daemon restarts mid-batch. Their on-disk work was recovered, independently re-verified (the coordinator personally re-ran the module wiring fix, the full gate, and the fresh-DB sequence), and a specs-first audit was run against the uncommitted code before it was committed — one real bug was caught that way (explicit `couponCode: null` falling into the legacy pin branch). One early builder report claimed commits that did not exist on disk; **no number in this document comes from a builder report — all gate figures are the coordinator's own runs.**
- **Referral drop on edit** (above): re-evaluation removes the order's own referral discount under the evaluator's first-use rule; it is surfaced via `referralDropped`, but a merchant editing an order that legitimately carries a referral discount will see the total rise. Future fix candidate: a self-exclusion in `resolveReferral` for surgery contexts.
- **Bundle re-allocation** uses per-unit prices from `allocateBundle`; the Σ totals == impliedPrice × qty identity is spec-proven for divisible allocations — the same per-unit floor caveat EC29 documents for placement applies to indivisible ones.
- **Delivery recalc** depends on the customer's stored district and the catalog's current weights/zones — it answers "what would delivery cost for this cart today", which can legitimately differ from the original charge even when nothing about the address changed (zone edits, weight corrections). The original charge is the default precisely because of this.
- **Exactly-once:** surgery writes are sequential awaits in the codebase's style, not a single DB transaction — a crash mid-edit could leave items replaced before totals update. The audit + preview/apply symmetry make such a state detectable, but the residual risk is stated, not hidden (this matches the placement path's own discipline).
- **Profit truth bounds:** costs are only as good as the merchant's `ProductCost` entries and the as-of rule; a cost recorded late with an early `effectiveFrom` retroactively changes reported margins for old orders (history is the merchant's own record — the report reads it as written). The per-order profit for orders with an EC31 installment plan or an EC5 store draft does not adjust those artefacts (plan totals are snapshots by EC31's own rule; a draft-divergence warning rides item edits).
- **Khata dues are the EC19 truth, not the courier truth:** a delivered COD order whose cash sits with the courier still shows due until a verification/reconciliation records it — the same definition the OB1 due-collection queue uses, applied consistently.
- **No live proof:** no real WooCommerce/Shopify store, courier account, or production database was exercised. Both migrations still have to run on the real DB at deploy (owner's Dokploy redeploy), and surgery's store-order refusal means EC12 live verification remains the only path to lifting the v1 store boundary.
