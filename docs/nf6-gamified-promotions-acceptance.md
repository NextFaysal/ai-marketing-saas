## Design decisions (the ones the brief asked to be made and recorded)

- **Popup engine extension (OU8):** there is no second placement engine. `PromoCampaign` carries StorePopup's exact placement vocabulary field-for-field (`trigger` delay_seconds|scroll_percent|exit_intent, `delaySeconds`, `scrollPercent`, `frequencyDays`, `showOn`, `startsAt`, `endsAt`), the public list serves those fields per campaign, and the web `ShopPromotions` overlay reuses ShopPopup's own trigger + frequency-cookie pattern and requests a slot from the ED9 overlay queue (id `"promo"`, default priority — it never stacks over the shop popup; the pinned priority ladder was deliberately NOT modified). One campaign is presented at a time (first in-window, frequency-unmarked campaign).
- **Coupon path:** prizes are REAL `StoreDiscount` rows — the existing EC7 coupon engine's table, honoured at checkout by `DiscountsService.validateForCheckout` / `PromotionsService.evaluateCheckout`. Issuance copies the established issuer shape (`AbandonedCheckoutsService.issueRecoveryCoupon` / `DiscountsService.generateCampaignCodes`): unique random code with collision retry, `usageLimit: 1`, `perCustomerLimit: 1`, `origin: "gamified_promo"`, `sourceRef: "nf6:play:<id>"` / `"nf6:groupbuy:<joinId>"`. Exactly-once = the sourceRef pre-check before every create (the workflow engine's own guard pattern) + the play/join row's stamp; a failed issuance leaves the row unstamped and a later replay heals it through the same pre-checked path — never a fabricated code. Group-buy coupons are additionally product-scoped (`scopeType: "products"`, `scopeIds: [productId]`).
- **One play per phone:** the phone is normalised with the Fraud Shield's own helpers (`normalizeBdPhone` / `bdPhoneMatchKey` from orders/phone-utils); `BlockedPhoneService.isBlocked` (imported from FraudModule) refuses blocked numbers before any row is written; the `(campaignId, phoneKey)` unique on `PromoPlay` / `PromoGroupBuyJoin` is the enforcement, with the P2002 race caught and re-read. Number-format variants of the same subscriber number are the same play (spec-proven).
- **Server-side outcome:** the spin roll is `crypto.randomInt(0, totalWeight)` walked over the configured weights in `pickWheelSegment`. The play DTO carries a `claimedSegmentIndex` field that is *never read* — it exists in the type only to make the refusal explicit; specs prove a claimed win loses and a claimed loss wins when the weights say so. Public campaign shapes contain segment **labels only** — weights and prize values never leave the server (spec asserts the serialised shape).
- **Stock reservation — REJECTED, join record chosen:** `StockReservation` holds are anonymous checkout-session stock holds that expire silently and decrement sellable availability. A group-buy join is an identified (phone) commitment inside a merchant window; holding real stock for a group that may never form would block real sales, and a silent reservation expiry could not produce the required expiry state on the join. `PromoGroupBuyJoin` is the honest record. No stock is held, no payment is taken.
- **Group-buy expiry notification — record + staff visibility ONLY:** when the window passes unmet, open joins flip to status `expired` (lazily, on any status/list/public read of the campaign — no new job/sweep was invented) and remain visible in the dashboard campaign detail with phone numbers, so staff can contact joiners manually. **No SMS/WhatsApp/email send exists for this in v1 and none is claimed anywhere** — there is no honest existing per-joiner send path to ride (order notifications are order-bound; NF4's reminder sweep is booking-bound). Nothing is charged at any point; the no-prepayment rule is stated verbatim in the public payload (`noPrepaymentNote`), the storefront overlay, and the dashboard.
- **Group-buy unlock is lazy + eager:** the Nth join settles immediately; any later status/list read re-settles. Settlement issues coupons only to joiners without one (sourceRef-guarded), so re-settling is a no-op.
- **Permission area:** staff routes use `@PermissionArea("marketing")`, `organizations/:organizationId` base, TenantGuard + RolesGuard — writes OWNER/ADMIN, reads the booking/live-commerce four-role set. Public routes live on a separate `public/promotions` controller (the `public/shop` prefix belongs to the storefront controller; `public/booking` is NF4's), org resolved by shop slug + `shopEnabled`, unknown/disabled shop → 404.
- **Quiz mapping:** each option maps to exactly one target — `categoryId`, `tagSlug`, or `categoryName` (the org's own catalog vocabulary: `Product.categoryId`, `ProductTag.slug`, `Product.category`). Scoring tallies votes per key, ties broken by earliest first vote (deterministic). Result products are queried org-scoped + `status: ACTIVE` only; another org's product with the same categoryId can never appear (spec-proven). The dashboard create form (v1) authors ONE question with category targets; the API accepts up to 10 questions and all three target kinds.

## NOT BUILT / limits

- **Live proof of everything**: no migration has run on a real database, no shopper has played on a deployed shop, nothing is deployed. M30-style verification owed.
- **No customer notification send for group-buy expiry** (see decision above) — status record + staff-visible joiner list only. A future send could ride `ShopAccountService.sendShopSms`, but wiring it needs a settlement trigger (sweep/job) that v1 deliberately does not invent.
- **No group-buy checkout auto-application**: joiners use their issued coupon code at checkout like any coupon (the existing discount path). There is no phone-matched auto-apply at checkout in v1, and the storefront copy says exactly that ("কুপন কোডটি দিয়ে … নিজে অর্ডার সম্পন্ন করবেন").
- **No stock hold for group buy** (deliberate — see decision). A group can therefore unlock for a product that sells out meanwhile; the coupon remains a normal coupon and checkout's own stock rules apply.
- **Dashboard campaign EDIT is API-only in v1**: the page covers create, activate/deactivate, stats, plays/joins detail. The PATCH endpoint exists and is spec-covered via the service paths it shares, but there is no edit form yet (config changes = deactivate + recreate).
- **Dashboard quiz form authors one question** with categoryId targets only; multi-question / tag / category-name authoring is API-level in v1.
- **Wheel presentation is a labelled segment list + result**, not an animated canvas wheel — the mechanics (server outcome, coupon, one-play) are complete; the spin animation is a visual upgrade, not a mechanic.
- **One campaign presented at a time** on the storefront (first in-window campaign wins the overlay slot); no rotation/stacking of multiple promotions.
- Full API jest, fresh-PG, boot smoke and web build were **not** run — per the FB3 brief they belong to the coordinator's serial finisher.
