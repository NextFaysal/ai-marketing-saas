## Design decisions (the ones the brief asked to be made and recorded)

- **Migration — YES, `20261035000000` only, and why:** `OrderReview` had NO media field at all (EC15's `ownItem` literally returned `imageUrls: []` with the comment "OrderReview has no image field — never invented"), and `ExternalReview.imageUrls` belongs to a different table (pulled platform reviews), so there was no existing field that could honestly carry own-review media. Three additive nullable columns, nothing else: `OrderReview.media` (Json), `OrderReview.socialDraftPostId`, `Organization.googleReviewUrl`. `prisma validate` PASS.
- **Upload path — the existing machinery, no new path, no relaxed limits:** the RB3 pattern every media surface uses (`StorageService` presign of a quarantine PUT → browser PUTs straight to R2 → complete verifies HEAD size + magic-byte sniff via `detectMediaKind` → copy to the final key → `StorageRegistryService.register`, surface `"review"`). The type/size guards are the CREATIVE upload guards imported from `CreativesService` — `CREATIVE_UPLOAD_CONTENT_TYPES` (image png/jpeg/webp, video mp4/quicktime/webm), image cap 10 MB, video cap 50 MB — enforced identically at presign AND complete. Differences from the staff surfaces, by design: the credential is the reviewToken itself; the quarantine prefix `_quarantine/<orgId>/review/` binds the upload to the token's own org (a foreign org's key prefix is refused); uploads are accepted only BEFORE the review is submitted (a received review is the record staff moderate — the token holder cannot silently change it afterwards); max 4 items per review; storage-not-configured refuses honestly with the same Bengali message the other surfaces use.
- **Media privacy — keys, not URLs; EC15 untouched:** final objects land in the PRIVATE bucket and only their keys are stored on the review row. EC15's moderation behaviour is exactly as shipped (received + `isVisible` = public; staff hide/show via the existing moderation). NF8 changes none of it: public product-review payloads mint a 15-minute signed GET per media item ONLY for rows the public path already shows (received + visible); a hidden or not-yet-received review never reaches that mapping, so neither the review nor any media URL for it is ever minted on a public surface — spec (b) proves this including that `signedGetUrl` is never even called for the hidden/pending keys. The staff list (a staff surface) does expose hidden reviews' media so staff can moderate what they are approving. The token page itself learns only `mediaCount` — never keys or URLs. In local storage mode there is no signed URL to hand out, so `media[].url` is null (the MediaLibrary discipline) rather than a fabricated link.
- **Where the Google link setting lives:** `Organization.googleReviewUrl`, edited in the existing Settings → Branding card (the same card/PATCH that owns brandName/logo/primaryColor — the org/store settings surface the brief pointed at), validated by `normalizeGoogleReviewUrl` (empty clears; must parse as http/https — the SU5 RSS-link discipline; no host allow-list because Google issues several legitimate shapes and the link is never fetched server-side).
- **The Google offer — cleanliness statement:** the offer exists ONLY when (the customer's own already-submitted rating is 4–5) AND (the org configured its link). It is returned as data (`googleReviewOffer: { url } | null`) on the review page read; the web renders it as a plain external link the customer may choose to open. **There is NO auto-redirect anywhere** (no navigation code touches this URL), **it is never offered before submission, never for ratings below 4, and never when the link is unconfigured.** **No incentive is attached to any rating by NF8**: nothing in NF8 gives, promises, or conditions any coupon, discount, credit or reward on a rating value or on posting a Google review, and the offer copy says so ("সম্পূর্ণ আপনার ইচ্ছা"). Pre-existing behaviour NF8 did NOT touch and does NOT extend: the CX12b-era `REVIEW10` display block on the review page predates NF8, is shown irrespective of the rating value, is not connected to the Google offer in any way, and its copy/mechanics were left exactly as shipped — flagged here and to the coordinator for the owner's separate decision, deliberately not silently rewritten inside NF8.
- **Social proof draft — through the existing engine, exactly once:** the staff action (`POST organizations/:orgId/product-reviews/store/:id/social-draft`, OWNER/ADMIN/MARKETING_MANAGER) calls `SocialService.createPost` — the Social Posts engine's single creation path, which is born `status: "draft"`; NF8 never publishes or schedules anything, staff publish the draft themselves from the Social composer. The caption is grounded in the review row only (stars from the real rating, the customer's own comment text, the product name); the product link follows the MS5 rule — `${webBaseUrl}/checkout/${slug}` only when the resolved product has a slug, otherwise no link (never fabricated). Target account: a staff-supplied account id is validated org-scoped + connected; otherwise the org's first connected account (the SU5 resolution order); no connected account is an honest Bengali refusal with nothing written. **Exactly-once:** `OrderReview.socialDraftPostId` is the claim — written immediately after creation; a repeat action finds the claim, loads that post org-scoped, and returns it as `reused: true` WITHOUT calling the engine again (spec-proven by call count). If the claimed post was deleted by staff, a fresh draft is created and the claim overwritten (documented recovery, not a duplicate of a live draft). "Approved" gate = EC15's: rating present + received + `isVisible !== false`; hidden or unreceived reviews are refused, foreign-org reviews 404.
- **Review media is NOT attached to the social draft:** `SocialPost.mediaRefs` reference `MediaAsset` rows of the social media library, while review media are private-bucket `StoredFile`s — attaching them would require either forking the media model or exposing private objects. The draft is the review text + product link, exactly as scoped; staff can attach media in the composer. Recorded as a limit, not silently dropped.

## NOT BUILT / limits

- **Live proof of everything**: no migration has run on a real database, no file has been uploaded to real R2 storage from the review page, no draft has been created against a real connected social account, nothing is deployed. M30-style verification owed (incl. the production CORS/bucket setup the direct-PUT flow needs, which the other surfaces already depend on).
- **Review media on the public product page (PDP)**: photos render through the existing `imageUrls` path (now real for own reviews); VIDEO items ride the payload (`media`) but the PDP component does not render video in v1 — video is viewable in staff moderation. No PDP component change was made.
- **No media removal/replacement** by the customer after a completed upload, and no staff media-delete action — moderation remains the EC15 hide/show of the whole review (which also hides its media everywhere public).
- **The social draft carries no review media** (see the design note above) and no per-action account picker in the UI — the button uses the API's default resolution (org's first connected account); an explicit account can be passed via the API.
- **The pre-existing `REVIEW10` display** on the public review page was left byte-identical (see the cleanliness statement) — reviewing/removing it is an owner decision outside NF8's scope.
- **Chat-captured reviews (CX12b chat path) cannot receive media** — media attaches only through the token review page's upload flow; a chat review's row simply has no media, and nothing claims otherwise.
- Full API jest, fresh-PG, boot smoke and web build were **not** run — per the FB3 brief they belong to the coordinator's serial finisher (note: `OrdersModule` now imports `SocialModule` + `StorageModule`; the boot smoke is the gate that must confirm the module graph).
