## Step-0 audit (code only)

- **Registry:** `apps/api/src/social/social.constants.ts` — `SOCIAL_ACCOUNT_PLATFORMS` was `["meta_page", "instagram", "tiktok", "youtube", "linkedin_page", "telegram", "threads"]` (plain strings in the DB, constants are the validation source of truth). - **SocialAccount model** (`packages/db/prisma/schema.prisma`): `organizationId, integrationId?, platform (string), externalId, name, username?, pictureUrl?, status (connected|disconnected|error), lastError, appSource (platform|own, CC4), healthCheckedAt, providerHealth…` with a unique `(organizationId, platform, externalId)` upsert key — **no schema change is needed for a new platform**.
- **Telegram (SN6)** structure: a plain client class (`telegram.client.ts`, injectable fetch, platform errors verbatim, nothing logged), connect logic inside `SocialOAuthService` reusing the ONE persistence path `persistOAuthAccount` (Integration + sealed `IntegrationCredential` via `encryptJson`, account upsert, supersede hygiene), a dispatch branch in `SocialPublishService.publishToPlatform` BEFORE the Meta flow, a pre-flight branch in `social-preflight.ts`, controller routes in `social.controller.ts`, client provider registered in `social.module.ts`, and web surface in the Social Posts page (connect form in `SettingsPanel`, label in `shared.tsx` PLATFORM_LABELS).
- **Threads (SN7)** structure: the same skeleton, OAuth-flavoured — `threads.client.ts` + `ThreadsPublisher`, `SocialOAuthService.threadsConnectUrl/handleThreadsCallback` with `SocialOAuthState` discipline (random state bound to org+user+platform+purpose, 10-min, single-use consume), a PUBLIC callback route on `SocialOAuthCallbackController`, refresh inside `ensureAccessToken`, platform-mode entry, web connect button + account note. **OU9 follows the Threads/YouTube skeleton, not Telegram's** (GBP is OAuth).

### 2. How Google connections already work in this codebase

- **Operator Google app:** platform-config `googleAppConfig` → `GoogleAppConfig { clientId, clientSecret, redirectUri? }`, resolved by `effectiveGoogleAppConfig()` (admin snapshot → env `GOOGLE_CLIENT_ID/SECRET`). The SAME app serves YouTube (SP9 social), the Connect Center Google pack (CC20) and — per OU1's repair — the org-LLM/platform-config tail. There is also a SEPARATE `googleOAuthConfig` for staff SSO (AB8) — deliberately not reused.
- **YouTube social flow (SP9):** `SocialOAuthService.youtubeConnectUrl` (scope youtube.upload+readonly, `access_type=offline` + `prompt=consent` so a refresh token is always issued) → public callback → token exchange via `YouTubeClient` (the Google OAuth client) → channel list → 1 = instant persist, many = `channel_pick` state with SEALED credential payload, zero = honest error. Token refresh in `ensureAccessToken` resolves the app by the account's `appSource` (CC28 own-app via `resolveTenantAppConfig(prisma, org, "google")`).
- **Connect Center GBP (CC20) already exists — and is a different row family:** `GoogleConnectService` kind `business` (provider `google_business`, scope `https://www.googleapis.com/auth/business.manage`, redirect segment `google-business`) stores an **Integration** whose `externalAccountId` is the v1 location resource `locations/<id>`, discovered by `GoogleClient.listBusinessLocations` (accounts via `mybusinessaccountmanagement.googleapis.com/v1/accounts`, locations via `mybusinessbusinessinformation.googleapis.com/v1/{account}/locations?readMask=name,title`). OU9 does NOT duplicate that Connect Center flow; it adds the **SocialAccount** family (`google_business_profile` / provider `google_business_social`) that the publishing machinery dispatches on. One honest consequence: the v1 location resource alone cannot address the v4 localPosts endpoint (see §3), so the social flow's own location listing keeps the account resource and composes the parent.
- **Gate precedents:** TikTok `TiktokAppConfig.audited` (operator declaration flag on the app config, literal-true only, env fallback) and OU2's Cloudflare `enabled` / OU5's verify-first patterns — OU9's approval flag follows the TikTok shape on the existing `googleApp` config.

### 3. GBP API reality — OFFICIAL Google documentation only

Fetched/read 2026-10-17 from developers.google.com (summarised, not quoted at length):

- **API-access approval is mandatory and per-project** — *Prerequisites* (https://developers.google.com/my-business/content/prereqs): create a Google Cloud project, then request access to the Business Profile APIs via the GBP API contact form ("Application for Basic API Access") and await approval; approval state is visible in the project's quotas — **0 QPM = not approved, 300 QPM = approved**. Applicants must manage a verified, 60+ day-old GBP with a business website listed.
- **Local posts** — *Create Posts on Google* (https://developers.google.com/my-business/content/posts-data) + the LocalPost resource reference (https://developers.google.com/my-business/reference/rest/v4/accounts.locations.localPosts) and its create method (https://developers.google.com/my-business/reference/rest/v4/accounts.locations.localPosts/create): `POST https://mybusiness.googleapis.com/v4/accounts/{accountId}/locations/{locationId}/localPosts` with a `LocalPost` body — `languageCode`, `summary`, `topicType` (required; `STANDARD | EVENT | OFFER | ALERT`), optional `callToAction { actionType, url }` (e.g. `ORDER`; `LEARN_MORE` is the generic website action in the same enum), optional `media[]` of `MediaItem { mediaFormat: "PHOTO", sourceUrl }` (**sourceUrl is the only supported MediaItem data field for a local post**), `event`/`offer` sub-objects for those topic types. Output-only: `name` (`accounts/*/locations/*/localPosts/*`), `searchUrl`, `state`, timestamps. The v4 Google My Business API remains the only localPosts surface.
- **Location listing** — Account Management API `GET https://mybusinessaccountmanagement.googleapis.com/v1/accounts` and Business Information API `GET https://mybusinessbusinessinformation.googleapis.com/v1/{account}/locations?readMask=…` (readMask required) — the exact calls the CC20 `GoogleClient` already makes; a v1 location's `name` is `locations/{id}`, so the v4 parent must be composed as `{account resource}/{location resource}`.
- **Reviews are a separate API surface** (v4 `accounts.locations.reviews`: list/get/reply) — a different resource family from local posts, with its own surface area. OU9 does not build it (see NOT BUILT).

**Design consequences taken:** (a) the approval state is an operator declaration on the platform Google config, default false; (b) connect is NOT blocked by the gate (OAuth is not a GBP API call — blocking it would hide the location list's real answer), but the location fetch surfaces Google's refusal verbatim and publishing refuses outright; (c) only documented request shapes are implemented — STANDARD posts with optional LEARN_MORE call-to-action and one PHOTO by sourceUrl; no EVENT/OFFER/alert, no video, no multi-media.

## NOT BUILT

- **Reviews — list / read / reply** (separate v4 reviews API surface): not built; `GBP_CAPABILITIES.reviews/reviewReplies` are literal `false` and the web account note says so.
- **GBP inbox / comments / insights / follower snapshots / health probe:** not built (capability flags false). The health service's existing fallback answers honestly that the check is not enabled for this platform.
- **EVENT / OFFER / ALERT local posts** (they need their documented `event`/`offer` sub-objects), **video or multi-media local posts**, **local-post edit/delete/list**, **location profile editing** (hours/attributes/photos via Business Information / Media APIs): not built — v1 is STANDARD text posts with an optional link and one photo.
- **API-access live proof:** impossible today — approval is Google's to grant to the platform project (application via the GBP API contact form, verified profile 60+ days, quota 0 → 300 QPM). No live GBP call has ever been made or claimed; all proof is mocked-HTTP specs.
- **Connect Center deduplication:** the CC20 `google_business` Integration and the new `google_business_social` SocialAccount are separate connections to the same Google account (the codebase's standing two-family pattern, exactly like YouTube's `youtube_social` vs the Google pack). No merging was attempted.
- **Own-app GBP caveat (honest):** a tenant connecting via their OWN Google app needs GBP API approval for **their own** project too — the platform gate flag describes the PLATFORM project; a wrong declaration or an unapproved own project still ends in Google's verbatim refusal at list/publish time, never a fake success. The publish gate itself reads the platform declaration for both app sources (the operator's word is the platform's policy switch).
