# OU7 (One-Umbrella) — Finance: Accounting-Lite — Acceptance

Built 2026-10-16 on branch `one-umbrella`, base `c3ad9d2e` → final HEAD
(see §6). **Local commits only — NOT pushed, NOT deployed, no migration
has run on any real database, nothing below is live-proven.** A small /
medium merchant can now keep formal books inside the SaaS — chart of
accounts, a derived double-entry journal, trial balance + balance
sheet, bank statement reconciliation — while the existing generic GL
export stays for their accountant. This is **not** a Tally/QuickBooks
replacement and no native Tally/QuickBooks file is produced or claimed.

## 1. Step-0 audit (before any build)

- **GC20 finance batch (existing, in `apps/api/src/finance/`)**:
  `FinanceService` owns expenses (OWNER/ADMIN, audited), ledger VIEWS
  (sales / COD receivable / courier settlements / mismatches / refunds)
  and the GC20.5 **GL export**; `FinanceReportsService` owns the GC19
  reports (discounts, refunds, payment_sales, category_sales,
  shipping_cost) + the profit report via `OrderProfitService`. Every
  existing "ledger" is a VIEW over real records — nothing persisted a
  journal, a chart of accounts, or a bank-reconciliation state. OU7
  adds exactly that missing layer and touches no existing figure.
- **GL-export account mapping (the ONE mapping, reused verbatim)** —
  `FinanceService.glRows`: per sold order Dr payment-reality account /
  Dr `Discounts`, Cr `Sales` / `Delivery Income` / `Tax Payable`,
  remainder Cr `Other Income` / Dr `Other Adjustments`; reality
  account = `Gateway Clearing` when a verified_paid txn exists, else
  `COD Receivable` (COD), else `Cash` (approved advances > 0), else
  `Receivable`; gateway fees Dr `Gateway Fees` / Cr `Gateway Clearing`
  (only when `feeMinor` is recorded); expenses Dr `Expense: <category>`
  / Cr `Cash`; completed refunds Dr `Refunds` / Cr reality account,
  amount-less refunds skipped **and counted in the export notes**.
  OU7's CoA seed and posting rules use these exact names — no second
  mapping was invented. One deliberate, documented difference: the
  journal recognises a sale against the receivable first and settles
  it when payment arrives (two-step), where the GL export books the
  reality account in one step. The GL export file is unchanged.
- **Source records that actually exist**: sold orders (`Order` +
  shipments for the sold predicate), `TenantPaymentTransaction`
  (verified_paid, `feeMinor`/`netMinor` stamped only when a fee rate
  is known), `PaymentVerification` (approved advances; `source`
  distinguishes `manual_advance` from `gateway_deposit` — the latter
  is created FROM a gateway txn, so posting both would double-count),
  `ReturnRequest` (completed + resolution=refund, `refundAmountMinor`
  sometimes null), `Expense` (8 categories incl. `salary`),
  `ReconciliationImport`/`ReconciliationLine` (courier settlements;
  matched lines stamp `CourierShipment.codCollectedMinor`),
  `WalletTransaction` / `PaymentRefund` (see NOT BUILT §4 for why
  these are not posting sources).
- **Estimated-profit honesty rules (existing)**: profit figures come
  from `OrderProfitService` with null-never-0 actuals; OU7 changes
  none of that and links to it instead of building a second P&L.

## 2. Design (binding discipline, as built)

- **Derived, never a second set of books**: journal entries are
  generated by posting rules over the source records above; each
  entry stores `sourceType` + `sourceId`. Hand entry exists only as
  explicitly `isManual` entries (below).
- **Idempotency**: `JournalEntry.idempotencyKey = ou7:<type>:<id>`,
  unique per org in the DB; a re-run counts `alreadyPosted` and
  creates nothing (spec-proven). The DB unique index is the backstop
  for concurrent runs (P2002 → alreadyPosted).
- **Posting status is honest**: sources that cannot post are listed
  with their reason — `gateway_deposit` verifications ("gateway
  লেনদেন থেকে তৈরি — দ্বিগুণ এড়াতে পোস্ট হয় না"), amount-less
  refunds ("পরিমাণ রেকর্ড নেই"), amount-mismatched settlement lines
  ("আগে reconciliation-এ মীমাংসা করুন"), payments whose order is
  missing. Nothing is silently dropped.
- **Periods are open / reporting-only**: no period locking exists
  anywhere and none is claimed; trial balance / balance sheet say so
  in their payloads and in the UI.

## 4. NOT BUILT (explicit)

- **Payroll-lite register** — NOT BUILT. A salary register would be a
  second record over the same money: salaries are already `Expense`
  rows with category `salary`, and they post to `Expense: salary`
  through the expense rule. Building a parallel register would break
  the one-set-of-sources discipline; recorded as the lowest-harm gap.
- **`PaymentRefund` as a posting source** — NOT BUILT (deliberate):
  gateway refund records and completed `ReturnRequest` refunds can
  describe the same money; posting both would risk double-counting.
  Refunds post from the return record (GL parity). Revisit only with
  evidence the two never overlap for the same refund.
- **`WalletTransaction` posting** — NOT BUILT: wallet credits are
  derived from the same verified platform payments already posted via
  `payment_gateway`; posting them too would double-count.
- **Period close / locking** — NOT BUILT and not faked: periods are
  labelled open / reporting-only everywhere.
- **Opening balances / migration of pre-journal history** — NOT
  BUILT: the balance sheet is cumulative from the first posted entry;
  a merchant's pre-existing capital can be entered today only as a
  manual entry (Dr Cash / Cr Owner Equity — the form supports it).
- **Bank statement formats beyond the documented CSV** (date,
  description, amount[, reference]; amount in taka, signed) — no
  bank-specific parsers, no PDF/OCR import.
- **Native Tally/QuickBooks files** — NOT BUILT, never claimed; the
  generic GL export remains the accountant hand-off.
- **Auto-confirm / auto-post scheduling** — NOT BUILT by design:
  posting is an explicit run, bank matches are human-confirmed only.
