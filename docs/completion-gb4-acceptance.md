## GC10 — Embedded checkout payment, delivered

- **Options are server-computed truth.** `TenantPaymentsService.publicPaymentOptions(orgId)` mirrors the initiation gates exactly: an OWN option appears iff the gateway row exists, is enabled, and creds decrypt (providers: sslcommerz/bkash at GC10; extended by GC11); a PLATFORM option appears iff the tenant enabled platform payments for that provider AND the platform actually has that gateway configured (`WalletService.platformCreds` non-null). Failure-isolated → `{ online: [] }`. Nagad never appears (its initiation honestly refuses — a rendered option that always fails would be a fake option).
- **Public payment state.** `GET /public/tenant-payments/state/:orgSlug?orderId=&orderNumber=` — order id + human number must both match (the initiatePublicPayment discipline; else 404). `verified_paid` wins over any newer attempt; otherwise the latest attempt maps initiated→`pending`, failed→`failed`, cancelled→`cancelled`; no attempts → `none`.
- **Shop placement.** `CheckoutDto.onlinePayment` (nested DTO, pair re-validated server-side by `assertPublicPaymentOption` — an unoffered pair is a 400 before any order write). Online placement is non-COD: `paymentMethod := provider`, COD rules skipped, the manual-advance note skipped, order note `[অনলাইন পেমেন্ট (${provider}) — যাচাই বাকি]`, response `paymentClaimStatus: "online_pending"`. Absent → legacy behaviour (COD + manual parity spec-proven).
- **Web flow.** Checkout renders online radios (sandbox badge when sandbox), hides the manual advance box for online selections; submit places the order, stores the result in sessionStorage exactly as before, then initiates and redirects to the gateway's real URL; an initiation error lands on the success page with `payment=initiate_failed` (the order exists, unpaid — stated as such). The success page polls the state endpoint (~4s, ~30 tries) and only the polled `verified_paid` may render "✅ পেমেন্ট যাচাইকৃতভাবে সম্পন্ন হয়েছে"; pending renders যাচাই চলছে wording, failed/cancelled render "পেমেন্ট সম্পন্ন হয়নি" + an "আবার পেমেন্ট করুন" retry. **The browser return (`?payment=verifying`/`received`) by itself never renders a success state** — spec-pinned in `lib/checkout-gc10.ts`.
- **GB3 leftover found + fixed:** `shopHome` nested `checkoutTrust` inside `settings` while the shop checkout page reads it at top level (the terms/CAPTCHA UI could not activate from the payload as read). Fixed additively: computed once, returned at BOTH levels, spec proves both present and deep-equal.
- **Single/Landing:** `paymentOptions` added beside `checkoutTrust` in both public payloads; the shared DTO carries `onlinePayment`; placement validates the pair, skips COD rules, stamps a distinct marker note, returns `online_pending`. **Deliberate limit:** their stored `paymentMethod` passes through exactly as before (their `isCod` derivation is paymentMethod-based — stamping `provider="bkash"` would make an online bKash order indistinguishable from a manual-bkash advance claim in the stored row; the distinction lives in the marker + response + the transaction row). No web initiation UI for single/landing — landing's response already carries `orderId` + `externalNumber` (initiation-ready); single's legacy `orderNumber` field remains the externalId (changing it would break existing consumers).

## GC11 — ShurjoPay + aamarPay: verdicts BUILD / BUILD (research-first)

Full research with per-claim official citations: `docs/gb4-gateway-research.md`.

- **ShurjoPay — BUILD.** Documented token-auth initiation (`POST /api/get_token` → `POST /api/secret-pay` → `checkout_url`) **and** an independent verification endpoint (`POST /api/verification`, also `/api/payment-status`). Sources: https://shurjopay.com.bd/developers/intregration-howto · https://documenter.getpostman.com/view/6335853/U16dS8ig · https://github.com/shurjopay-plugins/sp-plugin-nodejs. Built (v2.1 only): creds {username, password, prefix, optional storeId, sandbox} sealed; **verify-before-save is REAL** — a `get_token` call must succeed or nothing is saved (status `verified`). Confirmation: the return handler is a trigger only — it calls `/api/verification` and marks paid iff `sp_code === "1000"` + exact amount + currency; a non-1000 code records `failed` (with the provider's `sp_message` as the failure reason); a failed/unparseable verification call leaves the attempt `initiated` and the buyer lands on "verifying".
- **aamarPay — BUILD.** Documented initiation (`POST {base}/jsonpost.php`, store_id + signature_key → `payment_url`) **and** the Search Transaction verification API (`GET /api/v1/trxcheck/request.php`) returning amount/currency/status, plus a documented signed IPN webhook. Sources: https://aamarpay.readme.io/reference/initiate-payment-json · https://aamarpay.readme.io/reference/search-transaction · https://aamarpay.readme.io/reference/instant-payment-notification · https://github.com/aamarpay-dev/aamarpay-nodejs. Built: creds {storeId, signatureKey, sandbox} sealed; **no pre-transaction credential check exists** (like SSLCommerz) → saves honestly as `configured`. Confirmation: success POST and IPN are triggers only — the Search Transaction record decides (pay_status `Successful` + exact amount + currency). fail/cancel POSTs record `failed`/`cancelled`. The IPN listener URL is registered manually with aamarPay support (their process) — the route exists so a registered IPN works.
- **Sandbox pinning:** aamarPay's sandbox Search Transaction was REACHED from this environment with the public test store — a nonexistent tran_id returns `{"status":"Invalid-Data", …}` with no pay_status/amount; the build treats that as **unconfirmed, never failed** (pinned in the research addendum + specs). ShurjoPay's sandbox `get_token` TIMED OUT from this environment — the client is built to the documented shapes and parsed defensively; sandbox token/verification proof is still owed (M30).
- **Refunds: NO-BUILD for both** — neither provider documents a refund API; refunds stay manual via the provider dashboard, and no refund path was fabricated. Platform path unchanged: `initiatePlatformOrderPayment` still serves sslcommerz/bkash only (spec-verified refusals for the new providers).

## GC12 — Payment ops, delivered

- **Attempts = `TenantPaymentTransaction`, extended in place** (no parallel PaymentAttempt table — a second record would double-write and diverge). New `failureReason` is recorded failure-isolated at initiation failures (error message, 300-char cap), SSLCommerz IPN FAILED/CANCELLED, bKash callback non-success, ShurjoPay non-1000, aamarPay fail/cancel — bookkeeping can never break a payment. Staff API (`PaymentOpsService`): `GET payment-attempts` (status/provider/source/orderId filters, order number joined, pageSize capped 100) + `GET payment-attempts/:attemptId` (valId + ipnPayload; foreign id 404). `displayStatus: "expired"` is a DERIVED label for `initiated` attempts older than 24h — the stored status is never rewritten (a filter on it works off the same derivation).
- **Failed-payment recovery (staff-triggered only):** `POST organizations/:orgId/orders/:orderId/payment-link-resend` — refuses practice orders and already-paid orders (400); provider/source from the body or the order's latest attempt, re-validated against the server-computed options; creates a FRESH initiation (a new attempt row) and SMSes the gateway link to the customer via `ShopAccountService.sendShopSms`. The send outcome is audited (`tenant_payment.link_resent` with `sentVia`) and returned honestly — when no channel reaches the customer, `sentVia: "none"` and the link is still returned for manual sharing. **Conversation send was deliberately NOT built:** `InboxService` is not injectable in OrdersModule (InboxModule imports OrdersModule — the reverse edge would cycle); SMS-only is documented in the service header. No automatic retries.
- **Gateway fee tracking (tenant-entered rates only):** `feeBps`/`feeFixedMinor` on the gateway row, labelled "আপনার gateway-এর ফি হার". On `verified_paid`: own path computes `fee = amount·feeBps/10000 + feeFixed` in the same update that marks paid; platform path stamps the wallet-computed fee. Rates unset ⇒ `feeMinor`/`netMinor` stay **null** — reports show "ফি হার সেট করা হয়নি", never an invented default. **Found-and-fixed trap:** the global ValidationPipe materialises absent DTO fields as `undefined` own properties, so a `hasOwnProperty` presence check would have wiped fees on every creds-only re-save in production; the discriminator is `!== undefined` (codebase precedent), proven end-to-end with real pipe-produced DTO instances (absent → preserved, explicit null → cleared, value → set).
- **Fee report:** `GET payment-fee-report?from&to` (+ `.csv`) — verified_paid in the Dhaka-day range (default 30 days), grouped per provider+source: count, gross, null-aware fee/net with `withFeeCount`.
- **Tenant settlement view:** `GET payment-settlements?from&to` — OWN-gateway verified payments grouped by provider + Dhaka day (of the verified stamp, `updatedAt`), labelled in the UI verbatim: "আপনাদের রেকর্ড অনুযায়ী প্রত্যাশিত settlement — gateway-এর নিজস্ব প্যানেলের সঙ্গে মিলিয়ে দেখুন" (a records-based expectation, not the gateway's settlement truth). Platform-path settlement remains the wallet statement — linked, not rebuilt.
- **Web:** fee inputs on every own-gateway form (percent↔bps, taka↔minor, prefilled, always-send-current-values so an untouched re-save cannot wipe fees); a Payment Attempts panel on the Connect Center page (filters, expandable detail, resend button showing the returned link + sendNote verbatim); a failure-isolated "অনলাইন পেমেন্ট" section on the order detail; the accounting page's "গেটওয়ে ফি ও সেটেলমেন্ট" section with CSV download.
