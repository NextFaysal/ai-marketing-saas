## Design decisions (the ones the brief asked to be made and recorded)

- **Tier derivation:** lifetime spend = Σ `totalMinor` over the customer's orders in the codebase's canonical sold statuses — `completed | delivered` (the EC33 / `isSoldOrder` status half). Cancelled / pending / processing / returned / refunded / failed NEVER count; practice orders are excluded. The highest tier whose `minSpendMinor` the spend reaches wins (ties on a threshold → larger sortOrder). Spec (a) proves 300000 completed + 250000 delivered = Gold at a 500000 threshold while 900000 in each non-sold status moves nothing.
- **Tier recompute trigger (chosen):** the order-event reconciler — `StoreCreditService.onOrderTransition` is subscribed to the same bus events as the loyalty reconciler (`order.delivered / created / ingested / status_changed / refunded`) AND is called directly from `IntegrationsService.upsertOrder` on external status changes, exactly like loyalty/gift-cards; it recomputes the order's customer on every transition. Tier-definition create/update/delete also recomputes the whole org in-request, and staff recompute endpoints (one customer / whole org) exist for repair/backfill. `CustomerTier` is a derived cache of a pure function of the orders table — always rebuildable; `getCustomerTier` recomputes on read when no row exists yet.
- **PriceList binding shape:** the EXISTING `PriceList`/`PriceListItem` machinery, minimally extended — `PriceList.groupId` became nullable and a unique `tierId` FK was added, so a list is bound to a group XOR a tier (no fake group, no forked pricing). Resolution stays the ONE existing door, `PriceListsService.priceMapForCustomer`, used unchanged by shop quote / single-product / landing / POS line-builders: **a group list wins first (a negotiated price is more specific), the customer's tier list applies when there is no group list.** Spec-proven: a derived Gold member resolves the tier list's 80000 price through `priceMapForCustomer` + `pickGroupPrice`; with a group list at 70000 the group price wins; a non-member gets null.
- **Store credit ledger:** `StoreCreditEntry` is the sole truth — balance is ALWAYS Σ `deltaMinor` for (org, customer); there is deliberately **no balance column anywhere** (the loyalty pattern minus its cache). Entries are never edited/deleted; `balanceAfter` is a per-entry snapshot stamped in the writing transaction. Exactly-once rides the `(organizationId, sourceRef)` unique: `nf7:spend:<orderId>`, `nf7:spend-reversal:<orderId>`, `nf7:refund-credit:<orderId>:<refundKey>`; every writer claim-checks inside its transaction first.
- **Where the refund-to-credit setting lives:** `Store.refundToCreditEnabled`, DEFAULT FALSE, in the existing per-store refund settings area — the `Store` model beside EC5's `refundPushEnabled`, toggled by a new OWNER-only `PATCH commerce/stores/:storeId/refund-to-credit` beside the refund-push route, with the toggle on the commerce sync page beside Refund Push (owner decision 2026-10-13). **Gate resolution:** an order linked to a Store reads THAT store's flag; a native shop order (`storeId` null — native orders carry no Store row) reads "any store of the org has it on", the merchant's opt-in signal for their shop. While OFF: the API throws 403 and writes nothing (spec d), `pushState` reports the gate false, and the order panel does not render the option at all (the block is conditional on the server-computed flag; `refundToCreditOffered` is vitest-pinned default-false). `refundKey` is REQUIRED — the UI mints one per panel open, so a retried refund replays the first entry (`replayed: true`) and `refundedMinor` moves exactly once; a different key is a second legitimate partial refund; the amount is bounded by `totalMinor − refundedMinor`, judged again inside the transaction.
- **Checkout application pattern followed:** the loyalty/gift-card pattern end-to-end. The evaluator (`PromotionsService.evaluateCheckout`) reads NO credit tables — the storefront passes a snapshot (`StoreCreditService.checkoutSnapshot`, derived balance, failure-isolated) and the new step **3d** (after gift card, before tax; the credit also shrinks the tax base proportionally like loyalty/gift) applies `min(balance, requested?, payable)`; the shopper opts in with `useStoreCredit` (+ optional `storeCreditMinor` cap) on the existing Quote/Checkout DTOs; after the order exists, checkout calls `postPlacementSpend`, which re-verifies the order's customer (the priced customer and the debited customer can never diverge), re-clamps to the CURRENT derived balance and the order total inside the transaction, and posts exactly once per order. Partial application is therefore structural: applied = min(balance, order total).
- **Cancellation-before-delivery reversal:** the same reconciler reverses a placement spend when the order reaches `cancelled | failed` with a compensating `spend_reversal` entry (original debit untouched), exactly-once via its sourceRef — but ONLY before delivery: an order in a sold status, or with a delivered/partial_delivered shipment, is never reversed here (its spend stands; giving value back after delivery is a staff refund-to-credit decision). Spec (g) proves both halves.
- **Customer surface:** the EXISTING shop account page gains a credit + tier card (balance, history, tier name + lifetime spend) fed by `GET public/shop/:slug/account/store-credit` → `ShopAccountService.creditView` → the session-resolved customer's rows only. The shop checkout learns the balance with a probe quote (the loyalty probe pattern — the displayed quote is never replaced by the probe's totals) and shows the opt-in checkbox only when the balance is positive. **Staff surface:** tiers + per-customer tier/credit live on the existing dashboard Customers page (where loyalty already lives); no second account area and no new top-level page were built.
- **Permissions:** membership controller is `@PermissionArea("customers")` — tier writes, grants and refund-to-credit are OWNER/ADMIN; reads use the four-role read set. All money movements are audit-logged (`store_credit.granted`, `store_credit.refund_to_credit`, `store_credit.spend_reversed`, tier CRUD, `price_list.tier_item_*`, `store.refund_to_credit_toggle`).

## NOT BUILT / limits

- **Live proof of everything**: no migration has run on a real database, no checkout has spent real credit on a deployed shop, nothing is deployed. M30-style verification owed.
- **Store-credit spend is wired into the native SHOP checkout only** (the surface the brief's customer account + checkout language describes). POS, single-product checkout and landing checkouts do NOT offer credit in v1 — they also don't offer it falsely; their totals are byte-identical to pre-NF7 because the evaluator input is absent there. (Loyalty/gift were wired into those surfaces in their own packages; credit can follow the same one-line-per-surface pattern later.)
- **No credit expiry, no credit transfer between customers, no cash-out of credit** — credit is spend-only inside the issuing org, by design.
- **Refund-to-credit does not push a platform refund** — it is a local refund record (`refundedMinor`) whose destination is the ledger; the EC5 store refund push remains governed by its own separate `refundPushEnabled` gate and is not triggered by a credit refund.
- **Returns (RMA) `store_credit_note` resolution is unchanged** — it remains a record-only resolution; refunding a return into real credit is done through the order panel's refund-to-credit (gated as above), not by silently converting the note.
- **Tier price-list authoring is by product id** in the customers-page editor (mirrors the API shape); a product-picker UI for tier lists is a later polish — group lists have the richer editor today.
- **No tier-change notifications** to customers (no per-customer send path was invented for tier events), and no tier expiry/demotion grace periods — derivation is always current-spend truth.
- Full API jest, fresh-PG, boot smoke and web build were **not** run — per the FB3 brief they belong to the coordinator's serial finisher.
