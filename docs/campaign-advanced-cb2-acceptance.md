## CA6 — Overlap & conflict warnings ✅

Deterministic checks computed **only from the plan's stored targeting** (no platform call, no member data):

- **Same audience on 2+ ad sets** → readiness warning (key `audience`) naming the audience (resolved against our `AudienceRecord`s; a foreign id is shown as the bare id, never given an invented name) and the ad set names. Implemented as the pure helper `CampaignsService.audiencePlanFindings` (stable codes: `audience_shared_across_ad_sets`, `prospecting_without_exclusion`) surfaced by `readiness()`.
- **Include ∩ exclude** → `validatePlan()` structural **error**: an audience that is both included and excluded — directly via `excludedAudienceIds` or via an applied preset's own `externalAudienceId` — can never reach publish as a contradiction. Readiness inherits it through the existing structure check, so `ready` goes false.
- **Prospecting without exclusion** → readiness warning suggesting the exclusion presets. "Prospecting" is judged conservatively: funnel retargeting/retention layers never draw it; a set including a non-lookalike custom audience is warm by construction and never draws it; a lookalike-only set is still cold and does. Unresolvable include ids are treated as warm (fewer false warnings, never invented ones).
- **Overlap spike verdict (Meta, official docs, checked 2026-10-17): NOT CONFIRMED — no endpoint exists.** The Custom Audience node's documented edges are `adaccounts / ads / health / sessions / shared_account_info`; there is no overlap edge, and the legacy `/audienceoverlap` reach-estimation path is not a current documented API. Overlap exists only inside the Ads Manager UI tool. `audienceInsights` therefore keeps `overlap.status: "not_computable"` with the reason text replaced by this verdict (member hashes are never stored either, so local computation is equally impossible). Specs: `ca6-audience-conflicts.spec.ts` 5/5.

## CA7 — Audience performance history ✅

- **Migration** `20261030100000_ca7_audience_intelligence` (CB2's single migration): `AudiencePerformanceRollup` (per-audience totals) + `AudienceMembershipSnapshot` (CA8's table, landed here so CB2 needs exactly one migration). No existing table touched.
- **Aggregation** (`AudiencesService.refreshPerformanceRollups`, fixed **90-day** window, stated in every payload): REAL `DailyAdMetric` rows only, ad-set-level rows only (`adExternalId === ""` — the planPerformance counting rule, so per-ad rows never double-count), joined per ad set to the ONE audience it unambiguously used — exactly one distinct resolvable `customAudienceId`, or a `savedAudienceId` resolving to our `SavedAudience`. Ad sets naming 2+ audiences are **ambiguous**: excluded and counted (`adSetsAmbiguousExcluded`); sets naming a foreign audience are **unknown**: excluded and counted; sets with no audience are counted separately. Spend is **never split or guessed** across audiences. A rollup whose sets leave the window is visibly zeroed with a fresh `computedAt` on the next refresh instead of going stale silently. CPA/CTR are derived at read (one shared `AudiencesService.rollupView`), null on a zero denominator.
- **Surfaces**: Audience Studio records carry `performance` (null = the honest "তথ্য নেই" state); `GET campaign-plans/audience-sources` gains the additive `performance` block (rollups + live coverage note); `GET/POST organizations/:id/audiences/performance[/refresh]` added (declared **before** the `:recordId` routes so `performance` is never swallowed as a record id); `suggestPlan` facts gain `topAudiences` — top 3 by CPA requiring **≥ ৳500 attributed spend AND ≥ 1 conversion** (stated minimums, so one lucky click can't rank). Builder: performance column in the Audience Studio list.
- **Found on the way (fixed minimally, studio block only)**: the builder page's `StudioData` type had drifted from the service payload — it typed `audiences` + preset `name` where the service has always returned `records` + preset `label` (the CN6 specs assert `records`), so the lookalike source picker and preset buttons could never render correctly. The type and its two usages now match the service; stored exclusion-preset entries likewise render their `label`.
- **Saved-audience caveat (honest)**: ad sets reference a `SavedAudience` only via `targeting.savedAudienceId` when a client writes one; sets built by applying a saved audience's targeting inline carry no reference and are counted as without-audience. CN5-era ad sets therefore attribute to platform audiences, and saved audiences with no referencing set show "তথ্য নেই".
- Specs: `ca7-audience-performance.spec.ts` 6/6 (aggregation correctness, ambiguity/unknown exclusion with attributed-total proof, stale zeroing, empty-state honesty, studio attach, suggestPlan minimums).

## CA8 — Sync completion ✅ (Meta) / spikes documented (Google, TikTok)

- **(a) Full sync replaces append-only.** `refreshMembership` now diffs the record's CURRENT segment membership (the same `contactsFor` source creation uses) against the `AudienceMembershipSnapshot` the last sync established on Meta: additions upload via `POST /{audience}/users`; departures are **deleted** via Meta's `DELETE /{audience}/users` (spike-verified below). `graphDelete` gained an additive optional `params` argument (form-encoded body, mirroring `graphPost`); the no-params wire shape is byte-identical for the existing catalogs caller.
- **Conservative rules, all spec-proven**: segment source throws → error recorded on the record, **nothing changes on Meta**; source returns empty while the audience previously had members → whole sync **skipped**, reason recorded on the record + audit (`deletionsSkipped: true` in the result) — an audience is never wiped on a bad read; no snapshot yet (append-only era) → **baseline sync** (upload all, delete none, snapshot established, `baselineEstablished: true`); a DELETE failure persists snapshot = previous ∪ additions so departures **retry** next sync instead of being forgotten. `createCustom` seeds the snapshot at creation, so a created audience's first refresh can diff immediately. Evidence label: specs run against a **stubbed `fetch`** (the CN6 pattern) — the logic is proven, no live Meta call has exercised this path yet.
- **(b) Scheduled size/status refresh**: `refreshAllMemberships` (the existing `audience_refresh` automation job, unchanged) now also refreshes `approximateCount` + platform status for **every** built record (lookalikes included — membership sync covers custom only) and refreshes the CA7 rollups; each leg reports its own counts (`sizesRefreshed`, `sizeErrors`, `performanceRefreshed`), one leg failing never blocks the others. The automation module itself needed no change.
- **(c) Spike verdict — Meta member removal: CONFIRMED.** `DELETE {custom-audience-id}/users` is a current documented endpoint (listed in the Graph API v24.0 release notes among the Custom Audience endpoints; the CustomAudience/users reference documents "Remove users from custom audience" with the same `{payload: {schema, data}}` shape as the add path). Built, per (a).
- **(c) Spike verdict — Google Customer Match: NOT BUILT.** The upstream path exists (UserListService + OfflineUserDataJobService/UserDataService), but (i) this codebase's Google ads client is **read-only** (verify + metrics sync; zero Customer Match/user-list code anywhere — building means a new mutate client + consent handling, a new integration, not a sync completion), (ii) accounts need policy/payment eligibility this codebase cannot evidence, and (iii) Google has announced Customer Match uploads via the Google Ads API **cease 2026-04-01** in favour of the Data Manager API (reported via Google's developer communications), so the documented path is the retiring one. No code written, nothing faked.
- **(c) Spike verdict — TikTok audience sync: NOT BUILT.** TikTok's official Business API SDK documents DMP endpoints (`POST /dmp/custom_audience/create/`, `/dmp/custom_audience/file/upload/`, list/get/delete), so the upstream path exists — but this codebase's TikTok client is likewise **read-only**, and DMP requires a file-upload flow plus DMP advertiser permissions the existing connection does not carry. Per the task rule (build only if existing clients + scopes genuinely support it), documented, not built.

## CA9 — Geo intelligence ✅

- **(a) Per-plan region performance** (`GET :planId/region-performance`): aggregates the plan's stored `DailyAdBreakdown` `region` rows — real rows only, spend/impressions/clicks/conversions summed, CPA derived. **Honest shape**: breakdown rows are campaign-level (`DailyAdBreakdown` has no ad-set id), and the payload says so (`note`); no per-ad-set geo claim is made. Regions under the stated minimum (**2 stored rows**) are withheld and counted (`rowsBelowThreshold`), never merged into an invented "other". **BD division mapping**: exact match after case/space normalisation against the name variants Meta returns for Bangladesh — both spellings (`Chittagong`/`Chattogram`, `Barisal`/`Barishal`), bare and `… Division` forms, all 8 divisions → Bengali labels (ঢাকা বিভাগ …). Unmapped regions keep their **raw name with `division: null`** — never guessed (spec proves a near-miss like "Dhaka City" does NOT map).
- **(b) One-click draft** (`POST :planId/region-ad-set`, button "শীর্ষ region দিয়ে ad set"): creates a **local draft** ad set copying the source set's settings wholesale, targeting the top-N regions by conversions (**N = 3**, stated in the UI copy, with the ≥2-row threshold). Each region's Meta key is **resolved through Meta's own targeting search** (`adgeolocation`, exact name match, region-type preferred) — an unresolvable region is reported in `notCarried` and left out; a key is never guessed; if none resolve, the draft refuses. Stored as `targeting.regions: [{key, name}]`, which now flows through `buildTargeting`/`updateAdSet` and out to `geo_locations.regions` at publish. The draft has **no Meta id and nothing is published**; it is creatable on draft/rejected plans and on published plans with a live campaign (the only state region data exists in) — the response note states the live campaign is unchanged.
- **(c)** `suggestPlan` facts gain `topRegions` (org-wide stored rows, same ≥2-row + ≥1-conversion minimums; empty array when no rows exist).
- Builder UI: Region panel beside the CN7 breakdowns (loaded with the same button), per-region rows with division label + spend/conversions/CPA/row count, threshold + campaign-level notes, source-set picker, the draft button, and the notCarried report after creation.
- Specs: `ca9-geo-intelligence.spec.ts` 6/6.
