## Audit findings that shaped the build

- **PO flow (EC20, `purchasing.service.ts`):** statuses `draft | ordered | partially_received | received | cancelled`. The ONLY manual transitions are `draft→ordered` and `draft|ordered→cancelled`; `received`/`partially_received` are driven exclusively by the buyer's receive flow (which writes stock through InventoryService). **There are NO supplier-side transitions in the existing flow** — see the mapping below; none were invented.
- **Organization:** `slug` is unique; orgs are looked up by slug for the invite. **No cross-org concept existed anywhere** (the only cross-org code is the platform-admin portfolio rollup and OrgBrain's explicit "no cross-org read path" note) — NF12's agreement pair is the first, and it is explicit in the schema.
- **Order path:** `OrdersService.createManual` → `IntegrationsService.upsertOrder` (dedupe on `(org, source "manual", externalId = externalRef)`), the same path NF1 (comment→order) and AB5 (quote→order) ride. NF12 rides it unchanged.
- **Stock truth:** S1 global `Product.stockQuantity` is the counter; AX4 `StockBalance` per bin sums to it. Partner stock reads the SOURCE org's truth (bin Σ(onHand − reserved) when bin rows exist, else the product counter; null = untracked, displayed as "ট্র্যাক হয়নি", never a fabricated number).
- **Ledger precedents:** NF7's ledger-only truth (no balance column, exactly-once unique sourceRef) and OU11's payout legal gate — NF12's ledger is records-only in exactly that spirit; no wallet table is read or written anywhere in NF12.

## A) Supplier portal

- **Token discipline** = NF9/OrgInviteLink verbatim: raw token `randomBytes(32)` base64url returned ONCE at issue/rotation; at rest only SHA-256 hex (`SupplierPortalLink.tokenHash`, unique). One link per supplier — rotation overwrites the hash (old token dies immediately), revoke stamps `revokedAt` (terminal until staff re-issue), 30-day expiry. Staff issue/rotate/revoke/status live on the existing purchasing URL surface (`commerce/suppliers/:supplierId/portal-link…`); the dashboard dropship page hosts the management UI with the one-time link display.
- **What the portal sees:** the org's display NAME + the supplier's OWN purchase orders from that one org (id, status, dates, note, items with product name/SKU/quantities/unit cost/line totals, PO total, portal stamps). **Nothing else exists on the public surface** — there is no route to customer orders, customers, other suppliers, or any other org data.
- **Isolation:** every portal read/write is scoped by the link's `(organizationId, supplierId)` pair. Another supplier's PO id returns the same 404 as a missing PO (spec-proven: supplier A's token resolves only A's POs; A's confirm/ship on B's PO 404 and leave B's row untouched). Wrong token 404; revoked/expired Bengali 403.
- **PO TRANSITION MAPPING (the audited answer):**
  - Portal **confirm** → the EXISTING `draft→ordered` manual transition + `supplierConfirmedAt` stamp. Confirming an `ordered`/`partially_received` PO is an idempotent stamp-only no-op; `cancelled`/`received` refuse.
  - Portal **mark shipped** → **no status change** (no "shipped" status exists in the PO vocabulary and none was invented): stamps `supplierShippedAt` + optional `supplierShipNote` on an `ordered`/`partially_received` PO. `received` remains reachable ONLY through the buyer's own receive flow.
  - The portal can never cancel, edit items, or receive a PO.
- **Lead time:** the supplier edits `leadTimeDays` (0–365) + `leadTimeNote` on their OWN supplier record only.

## B) Dropship

- **Agreements:** `DropshipAgreement (supplierOrgId = orgA source, sellerOrgId = orgB seller, status pending|accepted|declined|revoked, invitedByOrgId, createdBy)`, unique per org pair. Invite by SLUG reveals only existence + display name (+ slug) of the counterparty — the invite response carries no other org data. The INVITED org's OWNER/ADMIN accepts/declines (controller role gate + service side check: the inviter cannot respond to their own invite). **Nothing is shared before acceptance** — offer creation, offer reads and listing creation all pass through the accepted-gate and refuse with 403 while pending/declined (spec-proven). Either side can revoke an accepted agreement: revocation stops NEW listings and NEW fulfilment orders; **existing order links keep their status mirror** (their supplier orders are real orders with their own lifecycle).
- **Offers:** `DropshipOffer` per (agreement, product), source-side only: the source org marks ITS OWN products eligible + sets `floorPriceMinor` (the wholesale unit value). The seller's offer view is minimised to product name, floor, active, and labelled partner stock.
- **Listings:** `DropshipListing` creates a REAL Product in the SELLER org (`source = "dropship"`, seller-set price) so the shop/cart/order paths treat it normally — with **`stockQuantity = null`**: partner stock is read LIVE from the source product and labelled `"পার্টনার স্টক"` + supplied-by org name in payload and UI; it is **never merged into the seller's own stock counts** (spec-proven). Seller price ≥ floor is enforced server-side (400 below floor; the UI pre-checks with the same rule but the API is the authority).
- **Order flow — wholesale-vs-retail minimisation (the careful part):** `processSellerOrder` scans the seller order's items for active listings and, per agreement, creates ONE fulfilment order in the supplier org through `OrdersService.createManual` carrying ONLY fulfilment-necessary data: item names/SKUs from the SOURCE product, quantities, and the customer's delivery name/phone/address. **Unit prices on the supplier order are the FLOOR (wholesale) values** — the supplier order total is the wholesale total; the seller's retail price and margin appear NOWHERE in the createManual payload or the created order (spec-proven by string inspection of the recorded payload). The one place both prices coexist is the seller-side `DropshipOrderLink.itemsSnapshot` + the ledger — and the supplier-side link view strips `retailUnitMinor` out (spec-proven).
- **Exactly-once (two stacked mechanisms):** (1) `DropshipOrderLink` unique per `(sellerOrderId, agreementId)` — the claim a replay finds and reuses (`reused: true`, no new order). The brief named `sellerOrderId` unique; the shipped unit is (sellerOrder × agreement) because one seller order can legitimately span two supplier agreements — the exactly-once guarantee per fulfilment order is identical, and a double placement/replay is spec-proven to create ONE supplier order and ONE link. (2) The supplier order's `externalRef` is the deterministic `dropship:<sellerOrderId>:<agreementId>`, so even if the link write were lost, createManual's upsert dedupe replays into the SAME supplier order.
- **Status mirror (READ MODEL):** `link.supplierStatus` refreshes from the real supplier order on every staff list read (+ the process/sync action). The seller order keeps its own lifecycle untouched; the seller's dropship view exposes `supplierStatus` + items + ledger state.
- **Cancellation propagation:** when the seller order is `cancelled`, sync cancels the supplier order through `OrdersService.updateOrder` — ONLY while pre-fulfilment (`pending|on-hold|processing`). A sold supplier order (`completed|delivered`) refuses: the mirror keeps the real status and `link.cancelNote` records the refusal reason (spec-proven both ways). The staff cancel endpoint follows the same rule and refuses a completed fulfilment with a Bengali reason. Supplier-side cancellation reflects to the seller view through the same mirror.
- **Commission ledger:** `DropshipLedgerEntry` (unique `dropshipOrderLinkId` = exactly-once), created when the supplier order first reaches a sold status (`completed|delivered`), with `retailTotalMinor` / `wholesaleTotalMinor` / `marginMinor = retail − wholesale` computed from the REAL line values snapshotted at fulfilment creation (spec-proven: 2 × ৳800 retail − 2 × ৳500 floor = ৳600 margin). **RECORDS ONLY — no payout execution anywhere, no wallet balance mutation; the API payload, the dashboard and this doc all state that payouts remain behind the OU11 legal gate.**
- **Web:** `/dashboard/commerce/dropship` — portal-link management, slug invite + respond/revoke, source-side offer/floor setting, seller-side listing creation (floor-checked), listings with partner-stock labels, dropship orders with supplier status + cancel, ledger with the records-only banner; nav entry in commerce-ops. Public portal page `/supplier/[token]`.

## NOT BUILT / limits

- **No payout execution — OU11 legal gate.** The dropship ledger is a record of margins only. No wallet credit/debit, no payout request, no settlement flow exists in NF12, and none is claimed. Any future payout work starts from the OU11 legal review, not from this ledger.
- **No cross-org anything beyond this design.** No cross-org product browsing/search, no cross-org customer/order reads, no shared catalog, no cross-org messaging, no platform-wide supplier directory. The agreement pair + the flows above are the entire cross-org surface.
- **No automatic checkout hook.** Fulfilment creation runs through `DropshipService.processSellerOrder` (dashboard action / API) — the seller storefront checkout was NOT forked to call it inline, so a dropship order's supplier fulfilment is created when staff process it (or a future automation job calls the same service method). The exactly-once design makes that call safe at any time, any number of times.
- **One fulfilment order per (seller order × agreement).** A seller order whose dropship items span two agreements creates one supplier order per agreement (two links); mixed carts (own products + dropship) send only the dropship lines to the supplier — the seller's own lines are never exposed.
- **Shipping/delivery charges do not cross.** The supplier order is priced from item lines at floor value only (no shippingMinor is passed); delivery-charge sharing between the orgs is a commercial term outside v1.
- **Portal is POs only.** The supplier cannot see dropship fulfilment orders in the portal (those live in the supplier org's own normal Orders UI, since the supplier org IS a platform org when it uses dropship); the portal exists for EXTERNAL suppliers who have no platform account. Supplier-side PO receiving remains buyer-only by design of the EC20 flow.
- **No live proof of anything:** no NF12 migration has run on a real database, no real supplier has opened a portal link, no real cross-org order has flowed. Fresh-PG + boot smoke are the coordinator finisher's gates for FB4; M30-style live verification is still owed.
- **Share-link delivery is manual** — staff copy the one-time portal link and send it to the supplier themselves; NF12 sends no SMS/WhatsApp/email itself (no honest per-supplier send path was in scope).
