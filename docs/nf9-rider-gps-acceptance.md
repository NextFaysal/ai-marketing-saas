## Design decisions (the ones the brief asked to be made and recorded)

- **Audit findings that shaped the build:** EC22's `Rider` is a staff-operated record (no rider login/app), and `DeliveryAssignment`'s active states are exactly `assigned | picked_up`. The CX6 shipment token (`CourierShipment.trackingToken`) is stored RAW — NF9 deliberately does NOT copy that; it follows the hashed-at-rest pattern (OrgInviteLink / payment links): `randomBytes(32)` base64url raw token returned once, only `createHash("sha256")` hex stored. Web `package.json` carries NO map library — none was added; every map surface is coordinates + an external Google Maps query link built from those coordinates.
- **Out-for-delivery vocabulary (the gate the brief flagged):** the codebase has no `Order.status = "out_for_delivery"` for native orders — `out_for_delivery` is the COURIER shipment status (CX6/lib `courier-status`, mapped verbatim there). The org's OWN rider expresses the same physical fact as a `DeliveryAssignment` in `picked_up`. The one shared rule (`rider-location-visibility.ts`, used by the service, CX6 and EC18) is therefore: out-for-delivery = order status normalised `out_for_delivery` OR shipment status normalised `out_for_delivery` OR the order's active assignment is `picked_up`. `assigned` alone never opens the gate. Both public tracking payloads were extended (not just one) so the rule holds on whichever tracking page the customer lands on; each extension is failure-isolated (a missing NF9 table reads as `riderLocation: null`, never an error, never a placeholder).
- **Customer visibility — all four conditions, server-decided:** (1) out-for-delivery per above, (2) an ACTIVE (`assigned | picked_up`) assignment for THIS order in THIS org, (3) the rider's share link currently sharing (exists, not revoked, not expired, rider switch ON), (4) a latest fix recorded FOR THAT assignment. Otherwise `riderLocation: null` and both pages render nothing — no placeholder, no stale shop position, no rider phone/address (the payload carries name + coordinates + fix time only).
- **Retention — the recorded choice:** current position = `RiderLocationLatest`, exactly one row per rider, UPSERTED per accepted ping (an out-of-order older ping joins the trail but never moves the latest fix backwards; a fix stamped >60s in the future is clamped to server time). History = `RiderLocationPing`, **capped at 200 rows per DeliveryAssignment** (`NF9_TRAIL_CAP_PER_ASSIGNMENT`), pruned oldest-first on insert (pruning is failure-isolated housekeeping — it never fails a ping). Nothing else about location is stored: no per-customer history, no indefinite trail.
- **Stale threshold — 5 minutes** (`NF9_STALE_THRESHOLD_MS`): fleet entries and tracking payloads carry the server's `stale` flag + real `ageMs`; the fleet page badges an old fix "পুরনো অবস্থান" and NEVER labels it live. The web mirrors the constant for display formatting only — the decision is always the server's.
- **Token lifecycle:** staff issue = create-or-ROTATE (one `RiderShareLink` row per rider; rotation overwrites the hash, so the old token dies immediately; the raw token appears in exactly one response and in the dashboard's one-time display box). Staff revoke stamps `revokedAt` + sharing OFF — terminal until staff issue again; the rider CANNOT resurrect a revoked or expired link from the share page (resolution refuses both with Bengali 403s). Links expire 30 days after issue (`NF9_SHARE_LINK_TTL_MS`). Wrong tokens 404. The ping DTO carries NO rider id — the token's rider is the only rider a ping can ever be written under (spec-proven with a forged `riderId` in the DTO).
- **Posting rule:** a ping is accepted only while the link is live AND the rider's sharing switch is ON AND the rider is active AND an active assignment exists; coordinates are range-validated. Stop-sharing (`POST public/rider/:token/stop`, the rider's own button; `start` re-enables) takes effect immediately: later posts 403 and the customer payload hides the location (spec-proven end-to-end).
- **The share page's honesty contract:** `/rider/[token]` states in plain Bengali that location is posted ONLY while the page is open (watchPosition, throttled to one post per 10 seconds), only while sharing is ON and an assignment is active — closing the page stops everything. **No background tracking is claimed or implemented anywhere.** The page shows the ON/OFF state in a full-width banner, the current assignment, the last accepted fix, and the link's expiry.

## NOT BUILT / limits

- **No native app, no background tracking** — location moves only while the rider's share page is open in the phone browser; the page says so verbatim. No push/keep-alive trick is used or claimed.
- **No map vendor / embedded map** — the web bundle has none and none was added; fleet + tracking surfaces show coordinates + an external "মানচিত্রে দেখুন" Google Maps link only.
- **No route optimisation, no ETA, no geofencing, no courier-provider GPS** — NF9 covers the org's OWN riders (EC22) only; third-party courier positions remain the courier's own tracking page (EC22 template link, unchanged).
- **No live proof of anything:** no NF9 migration has run on a real database, no real phone has posted a real GPS fix, nothing is deployed. Fresh-PG + boot smoke are the coordinator finisher's gates for FB4; M30-style live verification (a real rider phone, real browser geolocation permission, production `WEB_URL` for share links) is still owed.
- **Share-link delivery is manual** — staff copy the one-time link and send it to the rider themselves (e.g. by phone/WhatsApp outside the app); NF9 sends no SMS/WhatsApp itself, because no honest per-rider send path was in scope.
- **One active link per rider** — a rider with two phones uses the same link; there is no per-device token, no link-use audit trail beyond the tenant audit log entries (`rider.share_link_issued|rotated|revoked`), and no automatic expiry warning before the 30-day expiry.
- Full API jest, fresh-PG and boot smoke were **not** run — per the FB4 brief they belong to the coordinator's serial finisher (note: `DeliveryModule` gains `RiderGpsService` + `PublicRiderGpsController`; the module was already registered in `app.module.ts` since EC22, so the boot smoke is the gate that must confirm the new routes map).
