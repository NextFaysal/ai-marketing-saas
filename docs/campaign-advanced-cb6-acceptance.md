## CA23 — Advantage+ truth + app promotion ✅ BUILT (spike-first)

**Spike verdict (official Meta documentation, verified 2026-10-17 — summarized here in my own words from Meta's unified Advantage+ guide for the Marketing API):**

- There is **no field a caller can set to "make" a campaign Advantage+**. The old creation marker for automated shopping campaigns was retired: from Graph v25.0, asking for it at creation is an error, and the app equivalent met the same fate.
- A sales/app/leads campaign **is** Advantage+ when three practical levers line up: (1) the budget lives at **campaign level** together with one of the supported bid strategies (Meta recommends the uncapped lowest-cost strategy; cost cap, bid cap and min-ROAS variants also qualify); (2) **no placement targeting or placement exclusions on any ad set** (account-level exclusion lists are a different mechanism and do not disqualify); (3) at least one ad set runs with **Advantage+ audience switched on** (`targeting_automation.advantage_audience = 1`), or carries geo-only targeting.
- Whether a campaign actually qualified is **read-back only**: `GET /{campaign}?fields=advantage_state_info` answers with a verdict such as `ADVANTAGE_PLUS_SALES` / `ADVANTAGE_PLUS_APP` / `ADVANTAGE_PLUS_LEADS`; qualifying campaigns also report `smart_promotion_type: GUIDED_CREATION`.
- App promotion: objective `OUTCOME_APP_PROMOTION`; the ad set's `promoted_object` carries `application_id` + `object_store_url` (Meta's own example combines a catalog `product_set_id` with the app pair); optimization goal `APP_INSTALLS`.
- One documented negative: `existing_customer_budget_percentage` is **not** available on new Advantage+ campaigns — nothing in this build sends it.

**What shipped.** The structural emulation is gone for the true path. For an `advantagePlus` plan, publish now sends the campaign-level structure Meta's contract requires: `daily_budget` at campaign level (as before), the **one** campaign `bid_strategy` derived uniformly from the ad sets through the existing CN2 field mapping (mixed strategies/amounts across ad sets refuse at validation, naming the conflict, because a campaign carries exactly one bid), `is_adset_budget_sharing_enabled=false`, **no** bid fields on the ad sets, and **no placement fields in any targeting payload** — placement restrictions stored on an Advantage+ plan refuse at validation, naming the ad set and the offending fields, and `toGraphTargeting` suppresses them as defence in depth. After creation, the campaign's `advantage_state_info` is read back and stored **verbatim** on the plan (`CampaignPlan.advantageState/Info/CheckedAt`) with a publish-log step and an audit row; a read-back of `DISABLED` is recorded loudly and does **not** fail the publish (the campaign exists; its state is Meta's fact). The builder shows Meta's read-back state — never the toggle — plus a plain Bengali explainer of what Meta's AI then controls (budget split, audience expansion, placements) and what the merchant gives up (per-ad-set budgets, placement choice). **App promotion (b) shipped in the same item:** `OUTCOME_APP_PROMOTION` as a plan objective, `APP_INSTALLS` goal, `CampaignAdSet.appId/appStoreUrl` (additive columns, DTO + builder form) mapped to `promoted_object { application_id, object_store_url }` (a set catalog pair rides along per Meta's documented combination), Advantage+ allowed on app plans with the `ADVANTAGE_PLUS_APP` read-back. Spec: `ca23-advantage-truth.spec.ts` 9/9 (stubbed Graph fetch — labelled stub evidence; no live call was made).

## CA24 — Pre-flight platform checks ✅ BUILT

`planPreflight` was policy-text only. `preflight()` now accepts an additive `{ includePlatform }` option (the controller's `POST :planId/preflight` passes it; readiness keeps its old cost profile), and a standalone `POST :planId/platform-preflight` returns the same checks. Three **live** reads through the plan account's existing `MetaPublishClient` (new read methods `getAdAccountState` / `getPageNode` / `getPixelNode`): (1) the ad account's `account_status` + `disable_reason`, normalized with the existing AD3 `metaStatusBucket` map — a Meta-confirmed DISABLED/CLOSED account is an **error** carrying `disable_reason` verbatim; restricted/unknown is a warning; (2) each plan Page still fetchable — an unfetchable Page is a warning carrying Meta's own error text; (3) each plan Pixel's `last_fired_time` — present is ok with the time, absent is a warning stating Meta reports no fire time. The honesty rule is pinned by spec: **any check that could not be performed is `not_checked` WITH the reason** (unreadable account, no Meta connection, no Page/Pixel on the plan) — never ok. The builder's preflight panel renders the three checks distinctly with status badges. Spec: `ca24-platform-preflight.spec.ts` 8/8 (stubbed fetch; read-only — nothing writes to Meta).

## CA25 — Asset picker intelligence ✅ BUILT

Verify first: `CampaignAd` carries `imageAssetId`/`videoAssetId` (Creative Library) and asset-derived ads carry a `creative:`/`media:` sourceRef on `imageUrl`/`videoUrl` (the CA5-era `getPlanFull` enrichment); `DailyAdMetric` ad-level rows carry `adExternalId`. New `GET campaign-plans/asset-performance` joins org plans → ads → each ad's `externalAdId` → `DailyAdMetric` rows with **level "ad" only** — campaign/ad-set-level rows are never attributed to a creative (the CA7 honesty rule, spec-pinned with 999,999-impression decoy rows). **Stated thresholds** (in the payload and the UI): a rating exists only with ≥ 1,000 impressions **and** ≥ ৳100 real spend from those rows; rated assets carry CTR/CPA computed from them, unrated ones carry nulls. The builder's ad-form, placement-override, edit-ad and variant selects now label every asset — "🏆 আগে ভালো চলেছে" + CTR/CPA only from the rated payload, otherwise "তথ্য নেই" — with a newest | best-performing sort toggle in which unrated assets always sort last. **Duplicate-upload warning:** the upload hash (sha256) is already persisted on `StoredFile` by the registry, so no migration was needed — `completeCreativeUpload` now looks up the same hash in the org and returns an additive `duplicateWarning` naming the earlier file and its first-upload time; the upload still completes (a deliberate re-upload is legitimate). Spec: `ca25-asset-performance.spec.ts` 6/6 (incl. the rb4 harness for the duplicate path).

## CA27 — AI feedback loop + ad versioning + catalog carousel ✅ BUILT (verify-first)

**Verify result:** plan snapshots (`CampaignPlanVersion`) freeze whole plan definitions at save points but there was **no per-ad before-image on edit, no per-ad version list/diff/restore** — CA27(b) builds exactly that missing layer; plan snapshots are untouched.

**(a) Winner traits.** `GET campaign-plans/winner-traits` + internal `winnerTraits()`: winners are (1) the ads of plans an A/B verdict named winner (`abTestResults` `winnerPlanId` only) and (2) proven performers — ads whose ad-level metric rows clear the CA25 bars with ≥ 5 conversions. Deterministic traits with counts: format, aspect bucket (from the creative's stored width/height), primary-text length bucket, CTA. A trait value is emitted only with ≥ 3 winners (`WINNER_TRAIT_MIN_SAMPLE`); below that it is suppressed and counted in the payload, never presented as a pattern. **Text-overlay is honestly excluded** — CA5's vision check produces generation-time warnings and stores no per-asset result; the payload says exactly that instead of guessing. The composed line ("আগের বিজয়ী বিজ্ঞাপনগুলোর বৈশিষ্ট্য: …" with real counts) rides `suggestPlan`'s facts + prompt and the `generateCopy` prompt as a labelled fact, following the CA7/CA9/CA20 facts discipline; absent traits add nothing.

**(b) Ad versioning.** `CampaignAdVersion` (migration above): `updateAd` snapshots the **before-image** whenever an edit actually changes content (16 content fields; external ids are never snapshotted — restoring content cannot touch the ad's Meta binding), and only then (a no-op edit creates no version). `GET :planId/ads/:adId/versions` (list), `GET …/versions/:versionId/diff` (field-by-field vs the current ad), `POST …/versions/:versionId/restore` — restore snapshots the pre-restore state first (source `restore`), so history is append-only and every restore is itself reversible. Builder UI: per-ad version list + diff view + restore with a confirm.

**(c) Catalog carousel assembly.** `POST :planId/ads/:adId/assemble-carousel`: cards are built from the product set's **real Product rows** under its stored criteria (category / maxPriceMinor / inStockOnly — a null stock count means "not known to be out of stock" and is stated in the payload), each card = the product's own name, formatted real price and image, linked at the ad's destination URL (no product URLs are invented). Existing manual cards are never stomped: without an explicit `replace: true` the call returns a **preview only**; applying rides `updateAd`, so the old cards are versioned first and restorable. Spec: `ca27-feedback-versioning.spec.ts` 6/6.

## CA28 — Landing pages from the builder ✅ BUILT (verify-first)

**Verify result:** the EC13 landing machinery (`LandingsService` + `LandingPage`) is product-bound and org-scoped, its public rendering composes the Product row's own name/price/images at serve time, and only **published** landings serve publicly (`getPublishedLanding`) — a plan-scoped page therefore needs **no new page type and no schema change**. `CampaignsModule` now imports `LandingsModule` (its import graph — Audit/Integrations/Commerce/Storefront/Inventory/Affiliates/Fraud/Connections — never imports CampaignsModule; the boot smoke below proves the wiring live), and `CampaignsService` takes `LandingsService` as an `@Optional()` **last** constructor parameter (existing spec constructions untouched; absent = honest refusal).

`POST :planId/landing` creates the page through `LandingsService.create` **unchanged** (its slug/status rules): the product resolves from the chosen ad, else the plan's first product-carrying ad, else an honest refusal; draft by default (publish only on explicit request). The response carries the `/l/{slug}` path plus the absolute URL on the feeds precedent (`WEB_PUBLIC_URL ?? APP_PUBLIC_URL`; null when unconfigured — stated, not guessed) and any existing landings for the same product. **Creation never touches the ad.** `POST :planId/ads/:adId/apply-landing` is the separate confirmed step: **published landings only** (a draft would send buyers to a page the machinery does not serve), written through `updateAd` so the previous link is snapshotted as a CA27 ad version first. Builder UI: per-ad "Landing তৈরি" button + offer panel with confirm-gated apply for the new or an existing published landing. Spec: `ca28-builder-landings.spec.ts` 7/7 (LandingsService stubbed at its public seam — the real service's render/slug behaviour is covered by the landings module's own specs; the creation inputs are asserted from the real Product row).

## NOT BUILT / honest limits

- **No live-platform proof for anything in CB6.** CA23's Advantage+ contract and CA24's field choices come from official Meta documentation; every publish/read path is proven only against stubbed Graph seams in specs. Whether a real account's token, app and catalog satisfy Meta's acceptance is M30-class live verification, still owner-gated.
- **CA23 read-back is one-shot.** The `advantage_state_info` verdict is read once, right after campaign creation (and on a resumed publish while unset). There is no scheduled re-check if Meta's state changes later; the stored timestamp says when the verdict was read.
- **CA24 pixel health is Meta's `last_fired_time` only.** There is still no per-pixel stored CAPI freshness signal beyond the CN3 readiness rows (stored state); the live check reports exactly what Meta returns and `not_checked`/warn otherwise — it does not synthesize a health score.
- **CA25 media-asset performance** depends on ads whose `imageUrl` carries the `media:` sourceRef; a MediaAsset picked by raw URL in older ads has no join key and stays unrated ("তথ্য নেই") — stated in the payload design, not papered over.
- **CA26 admin UI is minimal** (list, rename, re-describe, delete, create with JSON inputs) on the existing Settings page; the full JSON editor experience is the API's, not a visual builder. Blueprint `version` is a counter + audit trail, not a per-version snapshot store.
- **CA27 winner traits** cover format/aspect/text-length/CTA only; text-overlay is excluded for lack of a stored signal (above). Trait facts reach `suggestPlan` and `generateCopy` (the Creative Studio generation contexts in this codebase); image/video generation prompts do not consume trait facts.
- **CA28** offers landings for the plan's product only through the builder; section-level editing stays in the Landings pages (by design — the machinery's own surface), and applying a landing to an ad requires `WEB_PUBLIC_URL`/`APP_PUBLIC_URL` to be configured on the API, with an honest refusal otherwise.
