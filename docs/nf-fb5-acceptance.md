## NF13 — what shipped (detail: `docs/nf13-fraud-network-acceptance.md`)

- **Privacy is the product:** the only things that ever leave an org are an HMAC-SHA256 hash of the phone number and aggregate outcome counters. No raw phone is stored in any of the three new tables, the shared aggregate (`FraudNetworkPhoneStat`) carries **no org id at all**, and no name/order detail/message exists anywhere in the design.
- **Consent rule:** opt-in is per-org and OWNER-only, timestamped (`enabledAt`); orders created before opt-in NEVER contribute (no backfill), disabling stops future contributions immediately, and re-enabling stamps a fresh `enabledAt` so the disabled window never contributes. Contribution is exactly-once per (org, order) via the ledger's unique claim row, riding the `fraud_network_sweep` job (template default OFF per org) — the sweep is the only trigger.
- **Consumption with a suppression floor:** `lookup` returns counts only when ≥ 3 distinct orgs contributed (`FRAUD_NETWORK_MIN_ORGS = 3`); below the floor it returns `insufficient_data` with NO counts. Fraud Shield exposes the signal as an optional sibling field `networkSignal` — never merged into the org's own score, absent entirely when not opted in / unavailable / on any lookup error.
- **Key gate:** with `FRAUD_NETWORK_HMAC_KEY` absent the whole feature is honestly inert — settings report `available: false`, enabling refuses with a Bengali explanation, contribution/lookup/sweep report `unavailable`. There is never a fallback to plain SHA or a hardcoded key.

## NF14 — what shipped (detail: `docs/nf14-branded-app-acceptance.md`)

- **Audit headline:** NF14's core already existed from AB7/AB8 — per-shop PWA manifest (`buildShopManifest`: own name/colour/scope, honest icon rules), the install bar (with iOS manual instructions), and per-org VAPID push. NF14 rebuilt none of it.
- **The one real gap, built:** app-only offers — `StoreDiscount.appOnly` (staff DTO → service → serialize), a new public offers payload `GET /public/shop/:orgSlug/offers` (modelled on `publicFlashSales`, public-safe fields only), and a `ShopOffers` strip on the shop home page.
- **Display rule, stated honestly everywhere:** `appOnly` is a **display rule only** — app-only offers are hidden unless the shop is running standalone (installed app), but the code itself is never blocked and redeems normally on the web if shared; that sentence sits verbatim next to the dashboard toggle. Checkout evaluation does not read the flag (spec-proven identical results).
- Plus: one new cross-shop isolation test for the manifest builder, a per-shop dismissal-key test for the install bar, and a BrandingCard note stating plainly there is no separate app-icon upload.

## NF15 — what shipped (detail: `docs/nf15-agency-acceptance.md`)

- **Membership-only by design:** ORG14 (cross-org team view) was never built and owner decision D2 is still open, so NF15 has **no agency entity, role or setting** — an "agency" is a user with memberships in multiple orgs. The console (`GET /agency/console`) is built only on the caller's own ACTIVE memberships (`OrganizationsService.listMine`); a non-member org never appears (spec-proven by string inspection — its id, name, slug and numbers are nowhere in the payload).
- **Every number through the org's normal path:** orders/revenue from `AnalyticsService.overview` with the dashboard home's own date semantics, pending = tenant-scoped order count, unread = Σ `ChannelConversation.unreadCount`. Per-org failures are isolated (that card returns `summary: null` + "তথ্য লোড হয়নি"; totals sum only intact cards and count the failures). Totals are labelled sums of the listed cards, never "consolidated analytics".
- **Client-org creation delegates exactly** to `OrganizationsService.create` — TD1 slug governance and the ORG12 per-user cap apply unchanged (spec-proven through the real cap path); the page then mints an ORG9 invite link for the new org's team (a link files a join REQUEST, never a membership).
- **Commissions are records only:** `AgencyCommissionEntry` rows with validation (amount > 0, agency ≠ client, caller an ACTIVE member of the client org, period label ≤ 40 chars) and `recordsOnly: true` on every payload. Spec 5 instruments the wallet delegates and asserts **ZERO wallet calls** across all NF15 flows — no money moves; payouts stay behind the OU11 legal gate, stated in the verbatim web banner.

## NOT BUILT (consolidated, merged from the three per-item lists)

**Live proof — everything:** no FB5 migration has run on a real database, no real org has opted into the fraud network, no real sweep has contributed a real order, no real shop has had an app-only offer created or installed, no real agency user has opened the console or recorded a commission. **Nothing in FB5 is live-proven** (M30-style verification owed).

**NF13:**
- **`FRAUD_NETWORK_HMAC_KEY` is not set anywhere** — until the owner/operator sets it in the API environment (a deployment secret, never in chat/repo), production correctly reports the feature as unavailable and it stays inert.
- No removal of past aggregates — once merged, a contribution cannot be unmerged per org/order (by design; stated honestly in the settings card). Disabling stops only future contributions.
- No cross-check beyond phone — no device, address, name, IP or payment-instrument signals cross orgs.
- The sweep is the only trigger — no order/courier/checkout hook contributes; an opted-in org that never enables the `fraud_network_sweep` job contributes nothing, and contribution latency is the sweep interval, not real-time.
- No public/checkout-time network check, no customer-facing surface, no platform-admin per-phone view; the suppression floor (3) is a constant, not a setting.
- The aggregate merge is read-modify-write after the unique claim row (each order still counts exactly once per org); non-BD digit-string numbers hash their digit string, so two non-canonical spellings of one number could hash differently.

**NF14:**
- No native apps (no iOS/Android binaries, no app-store presence) — the "app" is the installable per-shop PWA that AB8 already shipped.
- No new push system (the existing per-org VAPID push is the shop's push), no service-worker change, no app-icon upload (the settings note says so instead of implying otherwise).
- No checkout/redemption change — `appOnly` is write-staff → read-public → display-filter only; campaign-code generation does not set the flag (defaults false).
- The offers strip renders on the shop home page only, and the payload is cached like other public catalogue reads (up to ~60s stale, the documented ED5 trade-off). Install-prompt limits are inherited: browsers that never fire `beforeinstallprompt` (iOS Safari) get manual instructions only.

**NF15:**
- **No cross-org team/admin view (ORG14)** — owner decision D2 is still open; nothing here shows a user an org they are not a member of, a cross-org member list, or another user's console.
- No agency entity, agency roles, or agency settings — nothing to configure; "agency" is only a user's set of memberships.
- No automatic commission calculation from revenue — amounts are typed in and recorded; nothing derives a percentage or amount from a client org's sales.
- No consolidated analytics beyond the labelled sums — no cross-org reports, charts, exports or digests.
- **No billing, payout, or wallet movement** — no wallet table is read or written anywhere in NF15 (spec-proven); payouts remain behind the OU11 legal gate.
- No client-org management beyond creation (delegated) + an invite link for a freshly created org; membership administration stays in the existing Team surface. Cards do not link into or alter any org's own pages.
